# 实机部署缺口与外部凭据清单

## 结论

截至 2026-07-24，本工作区不能启动真实入口、连接生产柜机或发起真实收款。安全的本地存在性核对显示：`apps/api/.env.production` 不存在；本地 `apps/api/.env` 未配置微信支付、支付宝、阿里云 PNVS 和 SmartVM 的生产凭据，且验证码提供方仍是非生产配置。`sandbox/.env.local` 即使保存了联调信息，也只能用于沙箱，绝不能复制到真实服务。

这只说明本工作区没有可验证的生产配置，**不代表组织一定没有这些账号或密钥**。服务器的 systemd 环境、云密钥管理器和供应商门户未在本次核对范围内；应由部署负责人按本文逐项给出“已取得 / 未取得”和不含秘密内容的验收证据。

当前代码把以下项目设为真实启动硬门禁：独立 `live` 数据平面、HTTPS 与 CORS、阿里云 PNVS、签名 SmartVM、单 API 写者、自动对账，以及**微信支付和支付宝两套真实凭据同时完整**。因此，若业务只准备微信支付，不能用空值或模拟值绕过支付宝：必须先调整生产门禁、支付产品范围和测试，再发布该变更。

## 使用边界

- 密钥、私钥、APIv3 Key、AccessKey Secret、管理员密码和 Bearer Token 只进入服务器密钥管理器或受限服务管理器环境；不要贴进聊天、工单、Git、截图、Figma、命令行参数或普通 `.env`。
- 本文中的“来源”说明去哪个主体账号或供应商控制台取得材料；它不是要求把材料交给开发者。交接时只报告变量名、是否已注入、证书序列号、账号主体、回调地址和预检结果。
- `apps/api/.env.production.example` 是无密钥模板；真实部署使用专用服务账号和独立 Linux 本地目录。生产数据、审计、上传、备份和金融租约不得与模拟环境共用。

## 运营商、客户管理员与商家：当前状态和上线目标

### 先给结论

当前代码还不是“一个运营商后台管理多个客户实例”的完整多租户系统。真实数据平面启动时明确只允许持久化**一个当前客户实例**；后台会话中的 `tenantId` 目前主要用于绑定该实例，业务用户、柜机、库存、支付、商家模板和系统配置尚未按 `tenantId` 分区。因此，不能仅靠给运营商账号增加权限，就安全地实现“管理每个实例”。

正式上线前必须二选一，不能混用：

| 部署模型 | 适用方式 | 运营商如何管理 | 客户管理员如何管理 | 当前实现状态 |
| --- | --- | --- | --- | --- |
| 每客户独立实例（当前代码可走的方向） | 每个客户独立服务进程、数据根、域名/子域名和密钥注入 | 运营商通过受控运维/实例入口进入某一个客户实例；每次操作只影响该实例 | 只登录并管理本客户实例 | 与当前“真实平面只能有一个当前实例”的约束一致，但仍需补齐权限收口 |
| 中心化多租户平台（未来能力） | 一个控制平面管理多个客户实例 | 先选择目标实例，再以审计过的运营商身份读取或操作该实例 | 所有业务查询、写入、AI、配置和审计都强制带本人的 `tenantId` | 尚未实现；需要数据模型、查询、缓存、文件、队列、回调和测试整体改造 |

### 目标权限矩阵

| 身份 | 应当能做什么 | 不应当能做什么 | 当前实现与缺口 |
| --- | --- | --- | --- |
| 运营商 / `super_admin` | 创建/停用实例、配置实例公开地址与运行状态、为指定实例配置集成、查看跨实例健康与审计；进入某实例后做受审计的支持操作 | 未选定实例时读写客户业务数据；以自身身份创建商家私有补货/模板；在浏览器展示任何原始密钥 | 当前拥有全部后台权限，但服务进程只承载一个实例；需要“目标实例选择 + 操作审计”或保持独立实例模式 |
| 客户管理员 / `admin` | 仅管理所属实例的人员、柜机、货品、规则、日常运营；使用 AI 工作台做本实例分析；提交该实例的 API/渠道配置变更 | 访问其他实例；读取已有支付、柜机、短信、AI 私钥；修改平台级部署、TLS、数据根或其他客户的配置 | 当前默认拿到全部实例级权限，包含 `system-settings:secret:view`；而系统设置又是进程级 `.env`，不是实例配置，必须拆分 |
| 商家 / `merchant` | 仅维护自身补货模板、登记自身补货、查看自身批次和领取去向 | 系统设置、支付/柜机/AI 配置、其他商家的模板和补货记录 | 数据归属逻辑基本按商家用户 ID 编写，但尚无租户字段；需要随实例模型一起隔离 |

### 配置和密钥的职责边界

下表定义的是**上线目标**，不是当前已经完成的权限。前文各表仍是每个变量的具体来源、用途和验收方式。

| 配置类别 | 材料通常由谁取得 | 谁可以提交/替换 | 谁可以查看原始值 | 说明 |
| --- | --- | --- | --- | --- |
| 微信支付、支付宝的商户材料 | 对应客户的收款主体，在微信/支付宝控制台取得 | 客户管理员可通过受控的“写入新值”流程提交；运营商负责实例级注入、轮换和验收 | 仅服务器密钥管理器/部署服务；后台页面一律不回显 | 客户负责商户主体和授权，运营商负责不泄露地接入本实例 |
| SmartVM `CLIENT_ID`/`KEY` 与设备交接包 | 柜机供应商按项目/实例交付 | 运营商；客户管理员可提交交接材料和非秘密设备映射 | 仅受控服务 | 设备、门、回调和签名规则必须与目标实例绑定 |
| 阿里云 PNVS AccessKey | 号码认证云账号的拥有方创建最小权限 RAM 服务账号 | 运营商或被授权的客户管理员通过受控密钥通道轮换 | 仅受控服务 | 短信签名、模板和 Scheme 可作为实例可见的非秘密配置；AccessKey 不能显示 |
| AI API Key、Base URL、模型 | 选定 AI 供应商及承担费用的一方 | 运营商，或客户管理员在本实例的写入新值流程中提交 | API Key 仅受控服务；Base URL/模型可按策略显示 | 客户管理员可使用 AI 工作台；是否允许其改模型/供应商要与费用和数据出境授权绑定 |
| 高德 Key/安全码 | 地图应用与域名所有方在高德控制台创建 | 目标实例管理员或运营商 | 仅允许受限域名的浏览器配置可下发；不应作为通用后台可读秘密 | 两者虽会发给浏览器，仍必须限制正式域名并避免跨实例复用 |
| 域名、TLS、数据根、备份、进程参数 | 运营商/基础设施所有方 | 运营商 | 不在业务后台展示 | `PUBLIC_BASE_URL`、证书、`VM_DATA_ROOT`、单写者和数据平面是部署边界，不是客户业务设置 |

实现上应将现有笼统的 `system-settings:*` 拆为“平台部署配置”“实例集成配置”“秘密写入”和“秘密读取”四类。生产系统通常不应存在面向后台页面的“读取秘密”权限；更新密钥应是写入新值、显示掩码和轮换时间，而不是回显旧值。当前 `admin` 默认包含 `system-settings:secret:view`，这是上线前必须收口的权限缺口。

### 为什么运营商打开商家工作台会失败

这不是“运营商权限不够”，而是前后端的两套角色判断互相矛盾：

1. `super_admin` 默认拥有 `merchant-workbench:view`，因此侧栏和 `/merchant` 路由会显示“商家工作台”。
2. 页面加载时并行请求模板、补货追踪和告警；其中补货追踪接口 `GET /merchant-restock-traces` 只接受领域角色 `merchant`。
3. 运营商和客户管理员在领域层都是 `admin`，即使后台身份分别是 `super_admin` / `admin`，仍会被该接口拒绝。页面使用 `Promise.all`，这一项失败就会使整个页面显示加载错误。
4. 只把接口装饰器改成允许 `admin` 也不够：服务层仍调用“当前用户必须是商家”的校验，并且按当前用户 ID 查询“自己的”补货数据。直接放开会得到空数据或把运营商身份错误地当成商家身份。

推荐修复是把运营商/客户管理员看到的内容独立为“商家运营视图”：先固定或选择一个目标实例，再只读汇总该实例下各商家的补货、批次和去向；商家本人的工作台继续只显示自己的数据。若以后需要代商家操作，必须显式选择商家、展示醒目的代操作状态、写入操作者/被代操作商家/原因/时间的审计日志，不能默认借用商家身份。

### 上线前的权限验收

1. 客户管理员登录后，只能读取和写入所属实例的数据；切换或伪造其他 `tenantId` 必须被拒绝。
2. 客户管理员可使用本实例 AI 工作台；AI 请求、缓存、用量和供应商配置不得跨实例混用。
3. 客户管理员可提交新的集成密钥，但任何接口、日志、导出和页面都不能返回旧密钥明文。
4. 运营商访问商家运营视图时默认只读且必须绑定目标实例；不能用运营商用户 ID 创建商家模板或把补货归属错误写给运营商。
5. 商家只看到自己的模板、批次、补货和领取去向；对其他商家 ID、模板 ID 或批次 ID 的直接请求必须拒绝。
6. 角色矩阵要覆盖前端菜单、路由、控制器守卫、服务层数据过滤和审计日志，避免再次出现“菜单可见但接口 403”的失配。

## 生产硬门禁：外部凭据逐项登记

### 微信支付与微信小程序

前置主体：一个已具备相应支付能力的小程序，以及已通过审核的微信支付商户号；两者必须在微信支付商户平台完成绑定。小程序侧开发项目 AppID 已保存在 `apps/mobile/project.config.json`，但它不是后端生产配置的替代物，仍需核对其与 `WECHAT_PAY_APP_ID` 和商户平台绑定记录一致。

| 变量 | 从哪里取得 | 在系统中的作用 | 保存边界与验收证据 |
| --- | --- | --- | --- |
| `WECHAT_PAY_APP_ID` | [微信公众平台](https://mp.weixin.qq.com/)的小程序“开发管理/开发设置” | 用 `code` 换取付款人 `openid`，创建 JSAPI 支付单，并核对支付回调中的 `appid` | 不是私钥，但由部署配置固定；记录 AppID 与商户号绑定已通过，不在文档记录 Secret |
| `WECHAT_MINI_APP_SECRET` | 同一小程序的开发设置；如已泄露应在平台重置 | 服务端调用 `jscode2session`，把小程序登录临时 `code` 换成 `openid` | 仅服务器密钥管理器；完成一次真实用户授权换取 `openid` 的受控验收 |
| `WECHAT_PAY_MCH_ID` | [微信支付商户平台](https://pay.weixin.qq.com/)的商户信息 | 指明实际收款商户，创建、查询和退款 API 都会使用 | 记录商户主体和 AppID 绑定关系；不得误填操作员账号或商户登录名 |
| `WECHAT_PAY_API_V3_KEY` | 商户平台“账户中心 / API 安全”由超级管理员设置 | 解密微信支付 v3 回调资源 | 32 位值只进密钥管理器；用真实支付回调证明解密成功 |
| `WECHAT_PAY_MERCHANT_PRIVATE_KEY` | 申请商户 API 证书时由商户安全保存的私钥文件 | 对微信支付 API 请求和小程序调起参数做 RSA 签名 | 以 PEM 安全注入；只记录证书序列号和轮换日期，绝不导出私钥 |
| `WECHAT_PAY_MERCHANT_CERT_SERIAL_NO` | 与上述商户 API 证书配套的序列号 | 告诉微信支付当前请求使用哪张商户证书 | 记录非秘密序列号；证书更新时与私钥同步轮换 |
| `WECHAT_PAY_PLATFORM_PUBLIC_KEY` | 微信支付商户平台的 API 证书/平台证书材料 | 验证支付和退款回调签名 | 从官方平台下载后安全注入；用回调验签和轮换演练验证 |
| `WECHAT_PAY_PLATFORM_CERT_SERIAL_NO` | 与平台公钥/平台证书配套的序列号 | 拒绝不是预期平台证书签发的回调 | 记录非秘密序列号；平台证书更新时同步更新 |
| `WECHAT_PAY_NOTIFY_URL` | 我方 `PUBLIC_BASE_URL` 派生，不是微信发放的密钥 | 支付成功回调地址，默认路径为 `/api/payments/callbacks/wechat` | 必须是同源 HTTPS、无查询参数；可留空让后端由 `PUBLIC_BASE_URL` 推导，但生产建议显式记录 |
| `WECHAT_PAY_REFUND_NOTIFY_URL` | 我方 `PUBLIC_BASE_URL` 派生 | 微信退款回调地址，默认路径为 `/api/payments/callbacks/wechat-refund` | 同上；退款验收必须验证该地址可达且验签成功 |
| `WECHAT_MINI_LOGIN_URL`、`WECHAT_PAY_API_BASE_URL` | 官方固定接口，不是申请材料 | 分别是小程序登录和微信支付 API 上游地址 | 保持官方默认值；不能指向自建或测试代理。详见[小程序下单](https://pay.wechatpay.cn/doc/v3/merchant/4012791897)、[APIv3 密钥](https://pay.wechatpay.cn/doc/v3/merchant/4012072195)和[商户 API 证书](https://pay.wechatpay.cn/doc/v3/partner/4012081992) |

还必须在微信公众平台配置正式 API 服务器域名，并在商户平台确认 AppID 绑定、JSAPI/小程序支付产品可用。支付回调不是“浏览器回跳”，所以必须在未登录条件下由微信平台访问并通过签名验证。

### 支付宝

前置主体：支付宝开放平台中已审核的应用、实际收款支付宝账户和已开通的 JSAPI/小程序支付能力。当前实现使用普通公钥模式；不要混用证书模式材料。

| 变量 | 从哪里取得 | 在系统中的作用 | 保存边界与验收证据 |
| --- | --- | --- | --- |
| `ALIPAY_APP_ID` | [支付宝开放平台](https://open.alipay.com/)创建并审核应用后，在应用信息页取得 | 标识下单、查询、退款和回调归属的应用 | 记录应用名称、主体和已开通产品；AppID 本身不是私钥 |
| `ALIPAY_SELLER_ID` | 与应用签约的实际收款支付宝账户信息 | 指定订单的实际收款方 | 必须是支付宝用户 ID，不是登录邮箱、手机号或应用 AppID |
| `ALIPAY_APP_PRIVATE_KEY` | 使用支付宝开放平台开发助手在受控机器本地生成，并向应用上传对应公钥 | 对请求参数签名 | 私钥仅服务器密钥管理器；不得上传或发送给任何人 |
| `ALIPAY_PUBLIC_KEY` | 支付宝开放平台“开发设置/接口加签方式”下载或查看的支付宝公钥 | 验证支付宝异步通知和响应签名 | 记录密钥版本和轮换日期；用真实通知验签证明正确 |
| `ALIPAY_NOTIFY_URL` | 我方 `PUBLIC_BASE_URL` 派生 | 支付异步通知地址，默认路径为 `/api/payments/callbacks/alipay` | 必须是同源 HTTPS、无查询参数；可由 `PUBLIC_BASE_URL` 推导，建议显式记录 |
| `ALIPAY_GATEWAY_URL` | 官方固定网关，不是申请材料 | 支付宝 OpenAPI 网关 | 保持 `https://openapi.alipay.com/gateway.do`；不要把沙箱网关用于生产 |

支付宝退款不单独使用 `ALIPAY_REFUND_NOTIFY_URL`；当前实现以原支付通知地址接收后续异步状态。参考[密钥配置](https://opendocs.alipay.com/common/02kdnc)、[异步通知验签](https://opendocs.alipay.com/open/200/106120)和[退款接口](https://opendocs.alipay.com/open/6c0cdd7d_alipay.trade.refund)。

### 阿里云号码认证 PNVS

前置主体：完成实名和开通的阿里云账号、最小权限 RAM 服务账号，以及号码认证短信服务中已审核的签名、模板和四种用途方案。旧 `ALIYUN_SMS_*` 配置或测试验证码不能代替 PNVS。

| 变量 | 从哪里取得 | 在系统中的作用 | 保存边界与验收证据 |
| --- | --- | --- | --- |
| `ALIYUN_PNVS_ACCESS_KEY_ID` | [阿里云 RAM](https://ram.console.aliyun.com/)中为部署服务创建的最小权限 RAM 账号 | 为 PNVS API 请求签名 | 与 Secret 成对保存于密钥管理器；权限只覆盖所需号码认证 API |
| `ALIYUN_PNVS_ACCESS_KEY_SECRET` | 同一 RAM 服务账号创建 AccessKey 时取得 | PNVS API 请求签名的秘密部分 | 只显示一次，丢失后创建新 Key 并轮换；不得写入 `.env.example` |
| `ALIYUN_PNVS_SIGN_NAME` | 阿里云号码认证短信服务控制台已审核的签名 | 标识验证码短信发送方 | 记录审核状态和主体，不记录密钥 |
| `ALIYUN_PNVS_TEMPLATE_CODE` | 同一控制台已审核的验证码模板 | 定义验证码短信内容；模板需包含 `##code##` | 记录模板审核状态和版本 |
| `ALIYUN_PNVS_SCHEME_NAME_APP_LOGIN` | 号码认证短信服务的方案管理 | 仅用于应用登录验证码 | 不得与其他用途共用；发送和核验必须使用同一 Scheme |
| `ALIYUN_PNVS_SCHEME_NAME_REGISTER` | 同上 | 仅用于注册验证码 | 同上 |
| `ALIYUN_PNVS_SCHEME_NAME_GENERAL` | 同上 | 仅用于通用验证验证码 | 同上 |
| `ALIYUN_PNVS_SCHEME_NAME_PASSWORD_RESET` | 同上 | 仅用于本人密码重置验证码 | 同上 |
| `ALIYUN_PNVS_REGION_ID`、`ALIYUN_PNVS_ENDPOINT` | 官方服务文档，通常为 `cn-hangzhou` 和 `dypnsapi.aliyuncs.com` | PNVS 请求区域和服务端点 | 不是密钥；保持官方值，避免私自改为代理 |
| `VERIFICATION_CODE_PROVIDER`、`VERIFICATION_CODE_PREVIEW_ENABLED` | 我方部署配置 | 强制真实 PNVS 且禁止将验证码预览返回给客户端 | 生产必须为 `aliyun_pnvs` 和 `false` |

正式预检默认只静态核对配置；只有明确加 `--send-sms --sms-phone <已授权号码>` 才发送一条真实短信。服务说明见[PNVS 短信认证](https://help.aliyun.com/zh/pnvs/user-guide/sms-authentication-service/)。

### SmartVM / 映翰通柜机平台

前置主体：供应商为该项目建立的**生产**租户和经书面授权的测试柜。SmartVM 凭据不能由本项目自行生成，也不能把 `pre.smartvm.cn`、沙箱 endpoint 或沙箱 Key 当作生产材料。

| 变量或材料 | 从哪里取得 | 在系统中的作用 | 保存边界与验收证据 |
| --- | --- | --- | --- |
| `SMARTVM_BASE_URL` | 映翰通项目/售后交付的生产 HTTPS endpoint | 所有柜机查询、开门和平台调用的上游地址 | 非秘密但必须是生产地址；在预检中只读查询指定测试柜商品 |
| `SMARTVM_CLIENT_ID` | 供应商为真实租户分配 | 标识调用方并参与请求签名 | 仅部署密钥配置；供应商应给出所属租户和有效期 |
| `SMARTVM_KEY` | 供应商为真实租户分配 | 对平台请求和回调做签名验证 | 秘密材料；建立轮换联系人和失效流程 |
| `SMARTVM_ALLOWED_NOTIFY_ORIGINS` | 供应商提供的回调/通知来源列表 | 限制可接受的外部通知 Origin | 仅精确 HTTPS Origin，不填路径、查询参数或通配符 |
| 生产设备码、柜门清单、货道/货品映射 | 供应商和运营方共同确认 | 将系统设备、柜门和商品与真实物理柜对应 | 不是环境变量，但缺失时不能安全开门或结算；必须留存版本化交接单 |
| 签名样例、回调字段、错误码、重试/重放规则 | 供应商书面接口交付 | 证明本系统能验证真实回调并安全恢复 | 用已授权测试柜的签名回调、重复回调和延迟回调验收 |
| `SMARTVM_*_CALLBACK_PATH`、`SMARTVM_PAYMENT_SUCCESS_PATH` | 我方路由配置，登记给供应商 | 柜门状态、结算、补扣、退款和付款成功的站内路径 | 只能是站内绝对路径；生产禁用未签名回调和自动伪造付款成功 |

供应商交付包至少应包含：生产 endpoint、租户凭据、允许来源/IP、设备与门清单、签名规则和样例、回调登记流程、错误码、时钟容忍/重试/重放规则、密钥轮换联系人，以及不影响其他柜机的受控测试授权。公开产品信息见[映翰通智能新零售系统](https://www.inhand.com.cn/products/smart-vending-system/)；实际生产参数以项目合同和供应商书面交付为准。

## 不属于第三方密钥，但同样阻塞真实上线的配置

| 配置或材料 | 来源 | 用途与要求 |
| --- | --- | --- |
| `PUBLIC_BASE_URL` | 我方域名、DNS、反向代理和 TLS 证书部署 | 唯一公开 HTTPS 根地址；支付回调、上传 URL、真实租户和外部通知均依赖它 |
| TLS 私钥与证书 | 证书颁发机构、ACME 客户端或受管 CDN/负载均衡 | HTTPS 的基础设施密钥，不放进 API 环境变量；到期、自动续期和私钥访问权限必须由运维负责 |
| `CORS_ORIGINS` | 已发布的后台和移动端 HTTPS Origin 清单 | 限制浏览器可调用 API 的来源；不要写路径、通配符或开发地址 |
| `VITE_API_BASE_URL` | 我方 `PUBLIC_BASE_URL` 的 API 路径 | 在 `apps/mobile` 与 `apps/admin-web` 的正式构建时写入，通常为 `https://<域名>/api`；它是公开客户端配置，绝不能承载密钥 |
| `VITE_SHOW_VERIFICATION_PREVIEW`、`VITE_ENABLE_PUBLIC_ADMIN_REGISTRATION` | 我方正式前端构建配置 | 生产应保持未设置或 `false`，不能暴露验证码预览或开放管理员注册 |
| `PORT`、`API_HOST`、`TRUST_PROXY_HOPS` | 我方反向代理和进程管理器拓扑 | API 监听与真实客户端 IP/HTTPS 判断依赖它们；只有明确代理层数时才设置 `TRUST_PROXY_HOPS`，不能信任公网直连的伪造转发头 |
| 微信小程序服务器域名、支付 AppID 绑定 | 微信公众平台和微信支付商户平台 | 小程序请求正式 API 且 JSAPI 支付能被平台认可；需确认仓库中的微信项目 AppID 与后端 `WECHAT_PAY_APP_ID` 一致 |
| 支付宝小程序/JSAPI 身份 | 支付宝开放平台和实际构建项目 | 真实支付宝 JSAPI 支付的应用主体与域名白名单；当前 `apps/mobile/src/manifest.json` 未声明 `mp-alipay`，上线前必须确认由哪个构建配置注入并做真机验收 |
| `VM_DATA_PLANE=live`、`VM_DATA_ROOT`、`VM_DATA_PLANE_ID`、`VM_PLATFORM_TENANT_NAME` | 我方部署负责人 | 隔离真实数据、审计、上传、备份和金融锁；真实库只能由受控初始化创建，不能复制模拟库 |
| `PAYMENT_MODE=real`、`PAYMENT_MOCK_ENABLED=false`、`WEB_CONCURRENCY=1`、`API_INSTANCE_COUNT=1`、`NODE_APP_INSTANCE=0`、`FINANCIAL_SINGLE_WRITER_ENABLED=true`、`PAYMENT_RECONCILIATION_ENABLED=true` | 我方服务管理器 | JSON 账本阶段防止模拟收款、双写和未处理支付/退款未知态；不能用 `auto`、`mock`、多 worker、cluster 或双实例 |
| `ALLOW_DEFAULT_BACKOFFICE_LOGIN=false`、`PUBLIC_ADMIN_REGISTRATION_ENABLED=false`、`ENABLE_LOCAL_MOCK_DEVICE_API=false`、`ENABLE_TEST_DEVICE_BOOTSTRAP=false` | 我方服务管理器 | 禁用默认后台密码、公开管理员注册、模拟柜机接口和测试设备预置；这些开关任何一个开启都会破坏真实入口边界 |
| `BUSINESS_TIMEZONE_OFFSET_HOURS`、`BUSINESS_DAY_START_HOUR` | 运营方确认的业务日规则 | 影响每日额度、统计和过期判断；上线前写入运营确认记录，不能在真实运营中随意改动 |
| `VM_INITIAL_SUPER_ADMIN_*` | 运营方创建的首个真实超级管理员资料 | 仅供一次性 `init:live-data` 初始化；其中密码属于一次性秘密，完成后立即移除注入 |
| `SANDBOX_ADMIN_TOKEN` | 真实库初始化后，以具备 `system-settings:view` 权限的管理员安全登录取得 | 仅用于 `sandbox:external-preflight` 读取受保护的支付自检；短期 Bearer Token，只能经受限环境或 `sandbox/.env.local` 提供，不能放在命令行 |
| Git 拉取凭据（仅私有仓库需要） | 代码托管平台的只读 Deploy Key 或受限机器身份 | 让服务器按发布流程从 Git 拉取；与支付、柜机密钥隔离，禁止使用个人长期高权限 Token |

`DATABASE_URL` 可能包含数据库密码，但当前真实业务主数据仍是受控 JSON 账本；填写它不会把系统切换到 PostgreSQL，也不是实机上线的当前前置条件。当前生产模板未要求 Redis、对象存储、JWT 签名密钥或第三方分析密钥；不要凭空新增这些凭据。

## 可选集成凭据

| 集成 | 变量 | 获取与作用 | 是否阻塞 |
| --- | --- | --- | --- |
| 高德地图 | `AMAP_WEB_KEY`、`AMAP_SECURITY_JS_CODE` | 在[高德开放平台](https://console.amap.com/dev/key/app)创建 Web/JS API 应用并限制正式域名；用于后台点位选择、地理编码和地点搜索 | 不阻止 API 启动；未配置时地图选择器不可用。二者会经 `/api/public-config` 发送到浏览器，应视为受域名限制的公开浏览器配置而非服务器私钥 |
| OpenAI 兼容 AI | `OPENAI_API_KEY`、`OPENAI_BASE_URL`、`OPENAI_MODEL`、`OPENAI_BASE_URL_EXACT_HOST_ALLOWLIST` | 在选定 AI 供应商控制台为本项目建立专用服务密钥；用于运营分析、异常诊断和建议 | 不阻止真实入口启动；启用后会外发业务上下文并可能计费。真实平面可配置，模拟平面必须留空 `OPENAI_API_KEY` |

## 取得与部署顺序

1. 确定真实域名、Linux 服务账号、独立数据根、备份位置和 TLS 终止位置，再创建预发布/生产的受控密钥注入通道。
2. 由业务主体分别完成微信小程序与商户号绑定、支付宝应用与收款主体签约、PNVS 签名/模板/Scheme 审核，并向 SmartVM 供应商索取生产交付包和测试柜授权。
3. 将秘密材料直接注入服务器密钥管理器；只把无密钥的变量填入部署清单。创建纯净 `live` 数据平面和首个非默认超级管理员后，立即移除初始化密码。
4. 在授权窗口运行本地完整门禁、服务器数据校验和 `sandbox:external-preflight`。预检只能在显式 `--send-sms` 时发送短信；默认 SmartVM 探测应保持只读。
5. 先验证生产就绪端点，再在独立测试柜上执行最小金额支付、退款、签名回调、重复回调和延迟回调；最后才开放真实柜机流量。

具体发布命令、备份停写窗口和公网验收见[发布与公网部署验证流程](发布与公网部署验证流程.md)。数据平面与配置约束见[真实入口、外部凭据与数据平面配置说明](真实入口配置与数据平面说明.md)。
