## 结论

支付、退款、SmartVM 付款回写和结果恢复链路已完成本地防御性重构，并通过当前单实例范围内的自动化与视觉验收。

但当前版本**不得按多实例生产架构部署**，也不能把本地结果表述为真实微信、支付宝、柜机或资金验收。上线前仍有两项 P1 门槛：

1. 支付账本是 JSON 快照，互斥和租约是进程内结构；多实例没有数据库唯一约束、事务、CAS 或共享锁。
2. 移动端“刷新服务端状态”只读取本地事件，不会主动查询支付渠道；支付成功但回调长期丢失时，仍需定时对账、后台待处理队列或受限的本人订单核对入口。

本轮没有连接公网机，没有调用真实支付、退款、短信、AI、地图或柜机，没有触发真实用户资金，也没有提交、推送或部署。

## 支付流程健康度

1. **付款人身份与业务归属——通过。** 真实渠道只接受服务端签发、绑定当前账号和渠道、一次性消费的付款身份句柄；原始付款人标识不下发到客户端，也不进入普通日志。
2. **支付意图与金额锁定——通过。** 金额只取服务端事件、预结算报价或补扣记录；分数金额、客户端篡改、错业务单、已退款或已完成订单在外呼前拒绝。
3. **渠道下单与重放——通过。** 顺序重复、并发重复和下单响应丢失复用同一支付意图；真实来源与模拟来源不会因运行配置切换而互相转换。
4. **支付回调与主动核对——通过（本地签名 Mock）。** 回调校验签名、时效、应用、商户、收款方、交易号、金额和币种；后台可主动查询微信/支付宝并复用同一入账路径，只有渠道明确关闭或跨宽限期多次确认不存在才释放意图。
5. **本地入账与 SmartVM 回写——通过（本地 Mock）。** 入账和柜机回写分阶段记录；重放只补偿未完成阶段。生产环境永不接受未签名 SmartVM 回调；即使误开自动转发，正金额结算也不能生成伪付款成功。
6. **退款意图与幂等——通过。** 所有退款入口必须明确提供正整数金额和稳定请求编号；在渠道外呼前落下唯一意图，同一编号严格绑定订单、金额和规范化原因。
7. **退款回调、查询与重投——通过（本地签名 Mock）。** 退款成功只在渠道事实和本地业务副作用都完成后展示；处理中或未知继续占用余额。渠道明确返回退款不存在时，仅复用原退款号重投，不创建第二笔退款。
8. **用户与管理员恢复体验——通过但有边界。** 移动端未知态禁用再次支付，只允许刷新本地状态；后台退款待确认态会在刷新后恢复原退款单，并只提供“向支付渠道核对退款状态”或关闭刷新，不提供第二次退款。

## 已完成的关键重构

### 支付与退款核心

- 支付和退款都先创建可持久化意图，再调用渠道；未知结果不会释放幂等锁。
- 支付、退款和 SmartVM 付款回写共用业务级金融协调器，并使用只能在当前临界区内生效的租约，拒绝伪造或过期租约。
- 支付成功和退款成功均拆分为“渠道事实”和“业务应用”两个阶段；后一个阶段失败时只补偿业务副作用。
- 旧退款入口不再允许缺省金额退化为整单全退；交易号、柜机号、退款请求号和金额全部必填。
- 退款原因只规范化一次，同一值用于校验、幂等比较、账本和渠道外呼。
- 服务端异常分数金额不再四舍五入为可支付金额。
- 重复收款不会覆盖主交易；系统记录告警，并将重复款留给明确的纠错退款。

### 渠道协议与恢复

- 微信支付和退款回调使用官方 AEAD 信封解析，并绑定平台证书/公钥序列号、应用、商户、原交易、金额和币种。
- 支付宝回调和主动查询绑定应用、卖家、商户订单、渠道交易、金额与币种。
- 微信/支付宝支付均支持后台主动查询和安全关单；关单前后都查询，避免关闭已完成支付。
- 微信/支付宝退款均支持主动查询；退款不存在时复用原渠道退款号重投。
- 本地待确认退款以白名单摘要返回管理端；不包含渠道原始回调报文。

### 生产配置与 SmartVM

- 启动门禁和系统设置候选更新复用同一套生产配置校验。
- 支付和 SmartVM 信任边界配置只能写入待重启文件，不能热应用。
- 非法候选在写文件和 `ConfigService.set` 前拒绝，文件与运行态零副作用。
- 生产运行中禁止在线修改 `NODE_ENV` 或 `APP_ENV`，防止即时退出严格模式。
- SmartVM Gateway 在生产环境无条件拒绝未签名回调。
- 正金额结算即使配置误开自动回写，也仍等待已确认支付单；只有零金额业务可自动回写。

### 用户体验

- 移动支付未知态明确说明“刷新服务端状态不会再次发起支付”，微信和支付宝按钮保持禁用。
- 后台退款字段使用准确术语区分原渠道交易号、操作请求编号和本地退款单。
- 退款分为填写与最终核对两步；最终动作使用危险色，并显示订单、事件、柜机、交易号、请求号和金额。
- 渠道待确认时移除返回修改、取消和再次提交；如已有本地退款单，则允许复用原单主动核对。
- 页面刷新后可从服务端白名单摘要恢复原退款单、原请求号和金额。

## 与官方协议的防御性对齐

- 微信 JSAPI 支付的客户端返回不是最终支付事实，服务端应查单确认：[微信支付 JSAPI 支付业务流程](https://pay.wechatpay.cn/doc/v3/merchant/4012791870)。
- 微信支付通知可能重复发送，应验签并幂等处理：[微信支付回调通知注意事项](https://pay.wechatpay.cn/doc/v3/merchant/4012075420)。
- 微信退款通知使用加密资源信封：[微信退款结果通知](https://pay.wechatpay.cn/doc/v3/merchant/4012791906)。
- 支付宝未知交易状态通过查询接口收敛：[alipay.trade.query](https://developer.alibaba.com/docs/api.htm?apiId=757&docType=4)。
- 支付宝退款使用稳定 `out_request_no`，并可查询退款结果：[alipay.trade.refund](https://developer.alibaba.com/docs/api.htm?apiId=759&docType=4)、[alipay.trade.fastpay.refund.query](https://developer.alibaba.com/docs/api.htm?apiId=1049&docType=4)。

上述对齐来自源码与本地 Mock 测试，不代表真实渠道联调验收。
