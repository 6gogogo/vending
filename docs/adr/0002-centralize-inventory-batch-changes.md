# ADR-0002 集中库存批次变化 Module

## 状态

已接受

## 背景

补货、领取扣减、手工批次调整、调拨、盘点修正和撤销都会同时影响货品批次、库存移动、消费追踪和柜机库存同步。此前这些步骤分散在多个业务模块中，理解一次库存变化需要同时阅读取货结算、货品、用户、仓库、操作日志和柜机模块，后续迁移正式数据层时也很难确认事务边界。

## 决策

新增库存批次变化 Module，统一处理和批次变化强相关的写入：

- 创建和扣减货品批次。
- 写入和批次变化对应的库存移动。
- 创建和标记消费追踪。
- 执行调拨、盘点修正和撤销中的批次恢复或扣回。
- 触发柜机库存同步。

操作日志暂不放入该 Module。需要操作日志编号的消费追踪，允许先完成批次变化，再由调用方在操作日志生成后补写 `sourceLogId`。

负库存平衡是正式业务规则。当柜机平台回调显示实际扣减数量超过系统当前批次数量时，库存批次变化 Module 应创建负库存平衡记录，而不是抛错或吞掉差异。

## 影响

- 库存批次变化的核心写入集中在一个 Interface 上，业务模块不再各自拼装批次扣减、库存移动、消费追踪和柜机库存同步。
- `InMemoryStoreService` 继续作为首版内存仓储 Adapter，符合 ADR-0001；业务规则不直接依赖数组写入顺序之外的实现细节。
- 操作日志仍负责运营追踪和撤销入口，因此短期内调用方仍需要协调操作日志和消费追踪的关联。
- 新增 `npm run smoke:inventory --workspace @vm/api` 作为库存批次变化的行为烟测，覆盖补货、扣减、负库存平衡、撤销、调拨、指定批次扣减和盘点修正。

## 后续

- 引入正式数据库时，将库存批次变化 Module 内部写入映射为同一个事务。
- 如果操作日志和撤销规则继续变复杂，再讨论是否把“可撤销库存操作”深化成新的 Module。
- 新增库存变化场景时，优先通过库存批次变化 Module 扩展行为，再让业务模块调用。
