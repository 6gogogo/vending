# 运行数据受控修复流程

本流程用于修复 `npm run verify:api-data` 发现的结构性运行数据问题。它只适用于 API 已停止、金融单写者租约已释放、且已经保存原始恢复快照的维护窗口；不要在公网 API 仍承接业务时执行。

## 原则

- 默认命令只读，不会获取写锁、修改文件或创建临时数据。
- 修复计划和控制台输出只包含计数与 SHA-256 摘要，不输出货品编号、用户名、密码哈希、盐、回调内容或其他记录值。
- `--apply` 必须同时提供刚刚 dry-run 输出的源 SHA-256。摘要不匹配表示数据已变化，必须重新分析。
- 应用修复前会竞争金融单写者租约；已有 API 或维护命令仍持锁时，命令必须失败。
- 只有修复后全部结构完整性检查通过时，才会通过已有的原子写入路径替换 `store.json`。

## 先创建不可变恢复点

先停止 API、支付对账和其他写入运行数据的进程。保存原始文件、审计日志和上传目录的离线恢复快照，并记录 SHA-256；不要用初始化脚本或“清空数据”代替恢复点。

标准备份命令会拒绝结构已损坏的账本，因此这种场景必须使用受控原始快照。快照完成后保持停写，直到修复、校验和回滚演练结束。

## 生成只读修复计划

```bash
npm run repair:api-data
```

计划会报告以下计数：

- `malformedGoods`：缺失货品关键字段的记录；只有有完整主标识、且在整份 JSON 中没有外部精确引用时才可能自动删除。
- `zeroQuantityInventory`：数量为零的库存流水；只有没有订单、事件、批次、支付或其他业务锚点、且流水 ID 无外部引用时才可能自动删除。
- `orphanMerchantTemplates`：引用不存在货品的商户模板；只有模板 ID 无外部引用时才可能自动删除。
- `manualRequiredCredentialDuplicateGroups`：大小写无关的同名后台凭据组。系统绝不自动选择、删除、合并、改名或重置其中任一账号。

`canApply: no` 表示存在人工决策、外部引用或修复后仍无法通过完整性校验；此时不得使用 `--apply`。

## 人工决策项

以下事项必须由拥有业务归属信息的管理员确认并留存记录：

1. 每个重复后台用户名对应的真实人员、应保留的账号、需要停用或改名的账号，以及密码重置和旧会话撤销方式。
2. 缺少主标识的货品、已被其他业务记录引用的货品、带批次/订单/事件锚点的零数量流水，究竟应补全、冲正还是保留为审计证据。
3. 所有默认后台密码、模拟支付单、模拟柜机和真实第三方配置的处理方式。它们即使不构成结构错误，也会阻止生产就绪。

人工处理应通过受控迁移或经过审核的管理操作完成，不得直接编辑 JSON 后跳过校验。

## 应用已证明安全的计划

仅当 dry-run 显示 `canApply: yes`，且原始快照已验证后才执行：

```bash
npm run repair:api-data -- --apply --source-sha256 <dry-run输出的64位摘要>
```

命令成功后立即执行：

```bash
npm run verify:api-data
npm run backup:api-data -- --label post-repair --keep 30
npm run verify:api-data -- --latest
```

随后在隔离环境完成一次恢复演练、核心计数核对和生产就绪检查。任何一步失败都应保持 API 停止，并从先前的原始快照或已验证备份恢复，而不是继续人工试错。

## 与发布流程的关系

完成数据修复不等于允许上线。仍需满足 [发布与公网部署验证流程](发布与公网部署验证流程.md) 中的真实支付、短信、SmartVM、测试柜、权限、备份恢复、公网反代与生产就绪要求。
