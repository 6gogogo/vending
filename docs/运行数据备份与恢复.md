# 运行数据备份与恢复

本文覆盖首版本地持久化数据，目标是在公网首次投放前具备可执行的自动备份、手动恢复和基本校验。

## 备份范围

默认读取 `apps/api/.env` 中的路径：

- `API_DATA_FILE`：业务状态文件，默认 `apps/api/runtime-data/store.json`
- `SYSTEM_LOG_FILE`：系统审计日志，默认 `apps/api/runtime-data/system-audit.ndjson`
- `UPLOAD_DIR`：上传文件目录，默认 `apps/api/runtime-uploads`
- `API_BACKUP_DIR`：备份输出目录，默认 `apps/api/runtime-backups`

备份目录包含登录会话、密码哈希、业务日志和用户上传文件，必须按生产数据保护，不要提交到 Git 或公开传输。

## 手动备份

先校验当前运行数据：

```bash
npm run verify:api-data
```

创建备份并保留最近 30 份：

```bash
npm run backup:api-data -- --label pre-public --keep 30
```

校验最新备份：

```bash
npm run verify:api-data -- --latest
```

校验会核对清单结构、业务 JSON、每个已列入清单的文件大小和 SHA256，并拒绝清单未声明的额外文件。系统日志或上传文件只要已被备份，后续缺失、被替换、额外插入或变成符号链接都会让命令以非零退出码失败；不要只看控制台摘要而忽略退出码。

也可以校验指定备份目录：

```bash
npm run verify:api-data -- --backup apps/api/runtime-backups/<备份目录名>
```

## 自动备份

公网服务器上先手动跑通一次：

```bash
cd /home/vnc/111/vending
npm run backup:api-data -- --label manual-check --keep 30
npm run verify:api-data -- --latest
```

确认成功后添加 cron。示例为每天 03:15 自动备份并只保留最近 30 份：

```bash
crontab -e
```

```cron
15 3 * * * cd /home/vnc/111/vending && /usr/bin/env bash -lc 'export NVM_DIR="$HOME/.nvm"; [ -s "$NVM_DIR/nvm.sh" ] && . "$NVM_DIR/nvm.sh"; npm run backup:api-data -- --label daily --keep 30 >> apps/api/runtime-data/runtime-backup.log 2>&1'
```

定期检查：

```bash
tail -n 80 apps/api/runtime-data/runtime-backup.log
npm run verify:api-data -- --latest
```

## 手动恢复

恢复前必须停止 API，避免内存仓储继续写回旧数据：

```bash
fuser -k 4000/tcp || true
```

先校验要恢复的备份：

```bash
npm run verify:api-data -- --backup apps/api/runtime-backups/<备份目录名>
```

恢复指定备份：

```bash
npm run restore:api-data -- --backup apps/api/runtime-backups/<备份目录名> --yes
```

或恢复最新备份：

```bash
npm run restore:api-data -- --latest --yes
```

恢复脚本默认会先为当前数据再做一份 `pre-restore-*` 安全备份。只有在当前数据已经损坏、连安全备份都无法创建时，才使用：

```bash
npm run restore:api-data -- --backup apps/api/runtime-backups/<备份目录名> --yes --no-safety-backup
```

恢复会拒绝与 `UPLOAD_DIR` 或其他运行目标重叠的备份路径，并先把业务数据、日志和上传目录完整复制到同级暂存路径。每份暂存文件会再次按清单核对大小和 SHA256，暂存上传目录也必须与清单文件集合完全一致；只有全部暂存校验通过后才会逐项替换目标。可捕获的替换异常会回滚已经替换的目标。不要把待恢复备份放进当前上传目录。

### 异常中断边界

当前 JSON 文件阶段的“逐项替换 + 异常回滚”不是跨业务数据、审计日志和上传目录的断电事务。若进程被强制终止、机器掉电或文件系统在多项替换之间失效，可能留下同级的 `staging` / `rollback` 证据，或出现只替换了部分目标的状态；脚本不会把这种情况虚报为一次原子恢复。

遇到异常中断时：

1. 不要启动 API，也不要手工删除 `staging` / `rollback` 文件或目录。
2. 保存控制台输出、当前目标、暂存路径、回滚路径和 `pre-restore-*` 安全备份。
3. 对当前数据和备份分别运行校验，确认哪一组文件完整。
4. 在受控停机状态下，从已通过校验的完整备份重新执行恢复。

要获得真正的跨资源崩溃原子性，仍需引入可恢复 journal / 事务存储并完成断电故障注入演练；当前脚本不能替代该能力。

恢复后重新启动 API，并再次校验：

```bash
NODE_ENV=production nohup npm run start:api:built > apps/api/runtime-data/api.log 2>&1 &
curl -sS http://127.0.0.1:4000/api/health
npm run verify:api-data
```

## 常用选项

- `--label <标签>`：追加到备份目录名，方便区分 `daily`、`pre-release` 等来源。
- `--keep <数量>`：备份成功后只保留最近 N 份。
- `--backup-dir <目录>`：临时覆盖 `API_BACKUP_DIR`。
- `--latest`：使用备份目录中的最新备份。
- `--skip-system-log`：恢复时不覆盖系统审计日志。
- `--skip-uploads`：恢复时不覆盖上传目录。
- `--no-safety-backup`：恢复前不创建当前数据安全备份。

## 公网投放前最低要求

1. `API_BACKUP_DIR` 已确认可写，且不在 `UPLOAD_DIR` 内。
2. `npm run verify:api-data` 通过。
3. `npm run backup:api-data -- --label pre-public --keep 30` 通过。
4. `npm run verify:api-data -- --latest` 通过。
5. cron 自动备份已配置，并至少手动触发或等待一次成功记录。
