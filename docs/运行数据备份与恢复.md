# 运行数据备份与恢复

本文覆盖首版本地持久化数据，目标是在公网首次投放前具备可执行的自动备份、手动恢复和基本校验。

## 备份范围

模拟平面兼容读取 `apps/api/.env` 中的路径；真实平面必须使用 `VM_DATA_PLANE=live`、`VM_DATA_ROOT`、`VM_DATA_PLANE_ID` 和 `VM_PLATFORM_TENANT_NAME`，并从数据根派生全部路径。恢复前，真实库中唯一客户实例的 ID、URL、名称还必须分别与 `VM_DATA_PLANE_ID`、`PUBLIC_BASE_URL`、`VM_PLATFORM_TENANT_NAME` 一致：

- `API_DATA_FILE`：业务状态文件，默认 `apps/api/runtime-data/store.json`
- `SYSTEM_LOG_FILE`：系统审计日志，默认 `apps/api/runtime-data/system-audit.ndjson`
- `UPLOAD_DIR`：上传文件目录，默认 `apps/api/runtime-uploads`
- `API_BACKUP_DIR`：备份输出目录，默认 `apps/api/runtime-backups`

备份目录包含业务状态、密码哈希、业务日志和用户上传文件，必须按生产数据保护，不要提交到 Git 或公开传输。验证码、Bearer 登录会话和资料草稿只保留在进程内，不进入业务快照或备份；不要把备份当作会话恢复机制。

每份新备份清单都绑定 `dataPlane` 与稳定 `planeId`，并与其内部 `store.json` 的三个原始 marker（平面、实例、初始化来源）交叉校验。恢复前两者必须与当前受控部署配置完全一致；模拟备份不能恢复到真实库，真实实例 A 的备份也不能恢复到真实实例 B。`--latest` 会跳过 marker 不一致、旧版或损坏目录；旧版未声明数据平面的备份可以校验并保留为审计证据，但恢复会被拒绝。

## 手动备份

先进入停写窗口：优雅停止 API、支付对账和其他可能写入运行数据的维护进程，并确认金融单写者租约已经释放。`backup:api-data` 会主动取得同一把租约；如果仍有 API 写者在线，命令会失败，而不是生成无法证明一致性的在线副本。

然后校验当前运行数据：

```bash
npm run verify:api-data
```

创建备份并保留最近 30 份：

```bash
npm run backup:api-data -- --label pre-public --keep 30
```

校验最新备份：

```bash
npm run verify:api-data -- --latest
```

校验会核对清单结构、业务 JSON、每个已列入清单的文件大小和 SHA256，并拒绝清单未声明的额外文件。业务数据和系统审计日志都是强制项：当前运行态缺少审计日志、或备份清单未包含唯一的审计日志文件时，校验、备份或恢复都会以非零退出码失败。每个备份副本与清单在报告成功前都会同步文件；在 POSIX 文件系统上还会同步父目录。不要只看控制台摘要而忽略退出码。运行中的系统审计日志采用私有文件权限，并在每次追加成功前同步文件和父目录；审计写入失败会触发生产业务关闭，而不是被静默当作可用。

也可以校验指定备份目录：

```bash
npm run verify:api-data -- --backup apps/api/runtime-backups/<备份目录名>
```

## 自动备份与一致性边界

当前 JSON 账本阶段不支持“API 持续写入时由 cron 直接复制 store、审计日志和上传目录”的一致性备份。不要配置会在 API 在线时直接执行 `backup:api-data` 的 cron；该命令应因竞争租约失败。

自动化只能由经过演练的编排任务完成完整维护窗口：排空写流量与回调、优雅停止 API/对账、确认端口和维护进程已退出、校验、备份、校验最新备份、重新启动 API，并确认 `/api/health/production-readiness` 恢复为 200。不同服务器的进程管理方式不同，本仓库不提供会自行杀进程的通用 cron 示例。

在首次上线前，先手动跑通一次受控窗口中的备份：

```bash
cd /home/vnc/111/vending
npm run backup:api-data -- --label manual-check --keep 30
npm run verify:api-data -- --latest
```

每次受控备份后都检查：

```bash
npm run verify:api-data -- --latest
```

同时把停写、备份和启动编排任务的退出码与脱敏日志保存在发布记录中。

## 手动恢复

恢复前必须停止 API，避免内存仓储继续写回旧数据：

```bash
systemctl --user stop <api-service>
ss -lntp | grep ':4000' && { echo 'API 尚未停止，不能恢复。' >&2; exit 1; } || true
```

先校验要恢复的备份：

```bash
npm run verify:api-data -- --backup apps/api/runtime-backups/<备份目录名>
```

恢复指定备份：

```bash
npm run restore:api-data -- --backup apps/api/runtime-backups/<备份目录名> --yes
```

或恢复最新备份：

```bash
npm run restore:api-data -- --latest --yes
```

恢复脚本默认会先为当前数据再做一份 `pre-restore-*` 安全备份。只有在当前数据已经损坏、连安全备份都无法创建时，才使用：

```bash
npm run restore:api-data -- --backup apps/api/runtime-backups/<备份目录名> --yes --no-safety-backup
```

恢复会拒绝与 `UPLOAD_DIR` 或其他运行目标重叠的备份路径，并先把业务数据、同一时点的系统审计日志和上传目录完整复制到同级暂存路径。不能跳过系统审计日志，也不能从缺少该日志的备份恢复，以免破坏证据时间线。每份暂存文件会再次按清单核对大小和 SHA256，暂存上传目录也必须与清单文件集合完全一致；只有全部暂存校验通过后才会逐项替换目标。可捕获的替换异常会回滚已经替换的目标。不要把待恢复备份放进当前上传目录。

### 异常中断边界

当前 JSON 文件阶段的“逐项替换 + 异常回滚”不是跨业务数据、审计日志和上传目录的断电事务。若进程被强制终止、机器掉电或文件系统在多项替换之间失效，可能留下同级的 `staging` / `rollback` 证据，或出现只替换了部分目标的状态；脚本不会把这种情况虚报为一次原子恢复。生产启动检测到这类同级残留会直接拒绝加载运行数据，避免自动重启读取可能混代的快照。

遇到异常中断时：

1. 不要启动 API，也不要手工删除 `staging` / `rollback` 文件或目录。
2. 保存控制台输出、当前目标、暂存路径、回滚路径和 `pre-restore-*` 安全备份。
3. 对当前数据和备份分别运行校验，确认哪一组文件完整。
4. 在受控停机状态下，从已通过校验的完整备份重新执行恢复。

要获得真正的跨资源崩溃原子性，仍需引入可恢复 journal / 事务存储并完成断电故障注入演练；当前脚本不能替代该能力。在该 journal 与演练完成前，不能将恢复流程宣称为满足生产灾难恢复的断电原子性要求。

恢复后重新启动 API，并再次校验：

```bash
systemctl --user start <api-service>
curl -sS http://127.0.0.1:4000/api/health
curl -fsS http://127.0.0.1:4000/api/health/production-readiness
npm run verify:api-data
```

## 常用选项

- `--label <标签>`：追加到备份目录名，方便区分 `daily`、`pre-release` 等来源。
- `--keep <数量>`：备份成功后只保留最近 N 份。
- `--backup-dir <目录>`：仅在停服维护窗口内临时覆盖 `API_BACKUP_DIR`；生产环境只能使用已审核的私有本地备份根目录。
- `--latest`：使用备份目录中的最新备份。
- `--skip-uploads`：恢复时不覆盖上传目录。
- `--no-safety-backup`：恢复前不创建当前数据安全备份。

`API_BACKUP_DIR/repair-evidence/` 下的修复前取证归档不是可恢复备份，不能作为 `--backup` 或 `--latest` 的输入，也不会被 `--keep` 清理；应按审计证据单独保留。

## 公网投放前最低要求

1. `API_BACKUP_DIR` 已确认可写，且不在 `UPLOAD_DIR` 内。
2. `npm run verify:api-data` 通过。
3. `npm run backup:api-data -- --label pre-public --keep 30` 通过。
4. `npm run verify:api-data -- --latest` 通过。
5. 已完成至少一次隔离恢复演练：恢复后运行数据校验、核心计数和生产就绪检查均通过。
6. 已将加密备份复制到与公网主机不同的故障域，并记录可接受的 RPO/RTO；本机备份不能单独满足灾难恢复要求。
7. 如需自动备份，已为完整停写—备份—校验—启动—就绪流程建立并演练编排任务。
8. 生产承载使用支持目录同步的本地 Linux POSIX 文件系统；Windows、NFS、SMB、FUSE 等环境在补齐等价耐久性与权限验证前仅可用于开发或测试。
9. 未使用外部 `copytruncate` 或未纳入清单的审计日志轮替；要么禁用轮替并监控磁盘空间，要么先实现受控分段轮替和全量归档备份。
10. 启动与维护命令的运行路径预检已通过：数据、审计、上传、备份和金融租约互不重叠，且已有路径链不经过符号链接；服务用户 ACL、批准存储根与 Windows reparse point 仍须人工确认。
