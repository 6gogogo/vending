# 发布与公网部署验证流程

本文档是项目发布门禁。涉及公网服务器、正式后台、小程序正式体验版或生产配置时，必须按这里的顺序执行。

## 总原则

- 本地先跑最新代码并验证，通过后才提交 Git。
- 公网服务器只从 Git 拉取代码，不在服务器上直接改源码。
- 公网服务器拉取、构建或重启前，必须在停止写入并取得金融单写者租约后备份、校验当前运行数据。
- 公网服务器拉取后必须重新安装依赖、构建、重启服务。
- 发布完成后必须从公网地址访问后台、小程序和 API 做部署验证。
- 本地验证和公网验证是两件事：本地跑通不代表公网已经部署成功。
- 首版 `apps/api/runtime-data`、`apps/api/runtime-uploads` 的备份与恢复按 `docs/运行数据备份与恢复.md` 执行。
- `verify:api-data` 失败时，按 `docs/运行数据修复流程.md` 生成受控修复计划；不得直接编辑 JSON 或用初始化脚本覆盖运行数据。
- 当前 JSON 账本生产承载只接受支持目录同步的本地 Linux POSIX 文件系统；Windows、NFS、SMB、FUSE 等环境在具备等价耐久性与权限预检前只能用于开发或测试。

## 当前最终公网入口（优先于下方历史边缘方案）

本次上线的唯一链路是 **VNC Nginx HTTPS → WireGuard `10.66.66.2:5795` → Spark `vending-public-web.service`（内部受限 API relay）→ Spark 回环 API**。VNC 不再承载 vending Node API、静态站点、Unix socket edge 或私网 API relay；Spark 原始端口也不直接暴露到公网。完整的固定目标、健康门禁、root 切换和回滚命令见 [Spark 公网最终入口链路](Spark公网最终入口链路.md)。

文中旧的“Spark 私网 API 中继”“VNC 回环边缘中继”与相应 `/run/vending` socket root action 均是历史方案，保留仅供审计已存在资产；不得作为本次最终上线步骤执行。

## 1. 本地验证

先确认本地工作区是你准备发布的最新版本：

```bash
git status --short
```

本地必须在待发布代码和待发布运行数据副本上执行：

```bash
npm run verify:api-data
npm run check:local:full
```

`check:local:full` 已包含工作区类型检查、API/移动端/后台测试、库存与防御性冒烟、前端安全检查和各端构建。任何一项失败都不能进入提交步骤。涉及接口、权限、支付、上传、验证码、柜机回调、系统设置时，还要补对应的定向测试。冒烟测试必须明确访问的是本地地址，例如：

```text
http://127.0.0.1:<本地端口>/api
```

本地验证记录中要写清楚：

- 测试使用的 API 地址。
- 测试使用的后台地址。
- 小程序/H5 使用的 `VITE_API_BASE_URL`。
- 哪些核心流程已经跑通。
- 哪些真实外部流程没有覆盖，例如真实支付、真实柜机、真实短信。

本地开发后台运行在 `localhost`、`127.0.0.1` 或 `::1` 时，前端会自动阻止连接远程 API，并回退到 `http://127.0.0.1:4000/api`，避免本地测试误操作公网数据。只有在明确要用本地页面验证远程 API 时，才允许临时设置 `VITE_ALLOW_REMOTE_API_IN_LOCAL_DEV=true`，并必须在验证记录里写明。

## 2. 提交到 Git

本地验证通过后再提交：

```bash
git status --short
git add <本次需要发布的文件>
git commit -m "<本次发布说明>"
git push vending codex/UI
```

当前本地常用远端名是 `vending`，当前发布分支是 `codex/UI`。如果以后调整分支，以实际发布分支为准，并同步更新本文档。

不得提交：

- 真实 `.env`。
- 服务器密码。
- 第三方密钥。
- `apps/api/runtime-data/` 运行数据。
- `apps/api/runtime-backups/` 运行数据备份。
- 上传文件目录里的真实用户文件。

## 3. 公网服务器拉取

登录公网服务器后先进入项目目录：

```bash
API_SERVICE=vending-api-candidate.service
REPO_DIR="$(systemctl --user show "$API_SERVICE" -p WorkingDirectory --value)"
test -n "$REPO_DIR" && test -e "$REPO_DIR/.git" || {
  echo '未从受管 API 服务识别出 Git 工作树。' >&2
  exit 1
}
cd "$REPO_DIR"
# 之后的 Git 检出、依赖安装和构建均不得留下组可写文件。
umask 077
git status --short
```

不要套用历史发布目录。公网服务器工作区必须由当前受管 API 服务的 `WorkingDirectory` 识别且保持干净；如果存在未提交源码改动，先确认来源，不要直接覆盖。

拉取代码前，先进入受控停写窗口。`backup:api-data` 会主动竞争金融单写者租约；只要旧 API 或其他维护命令仍持有租约，备份命令就会失败，不能把在线复制品当作发布回滚点。

先通过当前进程管理器优雅停止 API、支付对账和其他可能写入运行数据的维护进程。使用 systemd 用户服务时可按实际服务名执行：

```bash
systemctl --user stop <api-service>
```

没有服务管理器时，向实际 API 进程发送 `SIGTERM` 并等待其退出；不要使用默认发送 `SIGKILL` 的 `fuser -k`。确认 API 端口已无监听、无残留 API/维护进程后，再备份并校验当前公网运行数据：

```bash
ss -lntH | awk '$4 == "127.0.0.1:8100" || $4 == "[::1]:8100" { found = 1 } END { exit found ? 0 : 1 }' && {
  echo 'API 尚未停止，不能备份。' >&2
  exit 1
} || true
npm run verify:api-data
npm run backup:api-data -- --label pre-release --keep 30
npm run verify:api-data -- --latest
```

备份完成后保持停写，直到新版本的生产就绪检查通过。发布记录必须保存旧 commit、新 commit、备份目录名、备份清单 SHA256、每条命令退出码和后续预检报告路径。

如果这是首次把备份脚本发布到服务器，且服务器当前代码还没有 `backup:api-data` 命令，可以先拉取代码但不要重启 API；完成 `npm ci` 后立即执行上面的备份和校验命令，再继续构建、停止旧进程和启动新服务。此后每次发布都必须在拉取前完成备份。

若当前 **simulation** 快照仅缺少本版本新增的 `manualVerificationGrants` 空数组，旧版本的校验会报出这一个集合缺失错误。此时只能在停写后先以 `git pull --ff-only` 拉取含兼容迁移的发布版本、且不安装依赖和不启动 API；随后立即用新版本执行 `verify:api-data` 与 `backup:api-data`，再继续构建和启动。任何额外校验错误、真实 `live` 平面缺失该集合、或该字段不是数组，均不得使用此例外。

### `admin` 后台密码维护（默认初始化或已知当前密码）

若需要初始化默认 `admin`，或已经知道当前 `admin` 密码并希望在 VNC 本机完成改密，先在 Spark 服务器 **VNC 本机终端** 执行无密码预检：

```bash
npm run preflight:first-backoffice-password:maintenance
```

预检复用正式维护的 VNC 终端、受管 systemd service cgroup、运行数据校验、运行平面与存储路径、唯一有效 `admin` 账号检查；预检脚本不读取密码、不创建备份、不取得金融单写租约，也不执行密码更新。为验证同一受管上下文，它会短暂停止并恢复 API；恢复启动仍可能产生常规启动审计或必要的状态归一化写入，成功后必须重新通过本机健康检查。预检失败时不得继续输入密码，而应保留终端显示的首条失败原因。

仅在预检通过后，执行受控密码维护：

```bash
npm run init:first-backoffice-password:maintenance
```

该维护命令不接收命令行参数，拒绝 SSH、管道、非交互终端、未知运行时 drop-in 与非 active 的 API。它不会读取、输出或覆盖 API 的 `Environment=`：而是在用户运行时目录临时创建只覆盖执行生命周期与 TTY 的 oneshot drop-in，因此继承当前 API 服务已经受控的运行数据平面；维护 job 会显式清除 Node 的可注入启动环境。维护执行顺序固定为：当前数据校验、同平面备份、最新备份校验、VNC 本机非回显输入；在显示任何密码提示前会先取得金融单写者租约，租约不可用时直接失败而不会要求输入密码。默认密码状态下，只需两次输入新密码；已经初始化的账号会先要求输入当前密码并立即验证，验证失败时不会索取新密码、不会写入数据，验证通过后才两次输入新密码。新密码全程不回显。一般性成功、失败，或收到 `SIGINT`、`SIGHUP`、`SIGTERM` 的取消请求时，运行器都会先停止维护 job；只有确认该 job 已停止，才会校验自己写入的 drop-in 摘要后删除它、重新加载 systemd、恢复 API 并检查本机健康端点。无法确认停止或检测到 drop-in 漂移均属于完整性事件：运行器关闭式保留现场，不删除或执行未知配置，需人工恢复。它只会操作当前受控数据平面中确为 `admin` 且角色为 `admin` 的有效账号，取得金融单写者租约、撤销旧会话、更新不含密码的业务操作日志和系统审计日志。成功后再从公网使用新密码登录。底层 TypeScript 维护脚本还会校验自己位于 `vending-api-candidate.service` cgroup，禁止从普通终端直接运行。

唯一 `admin` 的新密码最少 6 位；其他后台账号的新设、重置和常规改密仍执行各自更严格的密码策略。

### 唯一 `admin` 后台密码恢复（仅遗忘当前密码时使用）

当且仅当当前受管数据平面中已存在、启用且角色为 `admin` 的唯一 `admin` 账号，而其已设置的密码无法确认时，才可从 Spark **VNC 本机终端**执行：

```bash
cd /home/fivegogogo/vending/current && PATH=/home/fivegogogo/.nvm/versions/node/v22.22.2/bin:/usr/bin:/bin /home/fivegogogo/.nvm/versions/node/v22.22.2/bin/npm run recover:admin-backoffice-password:maintenance
```

只有忘记当前密码时才使用本节恢复命令；若知道当前密码，应使用上一节同一维护命令完成验证后改密，避免无验证覆盖。恢复命令没有任何业务参数：它拒绝 SSH、管道、非交互终端和非当前受管服务工作树；不会接收、读取、显示或保存密码。目标账号预检和金融单写租约都会在显示任何确认或密码输入提示前完成；通过后才会要求本机操作员输入固定确认文本 `RESET ADMIN`，再两次非回显输入新密码。恢复仅允许精确用户名 `admin` 且角色为 `admin` 的有效账号，不能选择其他用户名、租户或角色；会撤销该账号全部旧会话，并写入不含密码的业务操作日志和系统审计记录。

它复用首次初始化的停写、完整性、校验、同平面备份、单写租约、临时 drop-in 和 API 恢复门禁，但使用独立的锁和 drop-in，不能与首次初始化并发。维护失败、取消或恢复后健康检查失败时，按同一完整性策略恢复 API；检测到临时 drop-in 漂移则关闭式保留现场，等待人工处理。恢复完成后，只能从公网 HTTPS 登录页验证一次新密码；不得把密码、确认文本以外的交互内容、浏览器表单值或审计详情发到聊天、命令行参数、环境变量或日志中。

若该受管工作树曾在较宽松 umask 下检出过，首次执行维护前还必须收紧其启动与维护脚本链；下面的检查只接受当前服务用户拥有的普通文件或目录，拒绝符号链接和其他类型：

```bash
for path in \
  package.json \
  scripts \
  scripts/run-first-backoffice-password-maintenance.mjs \
  scripts/first-backoffice-password-maintenance.mjs \
  scripts/first-backoffice-password-maintenance-runner.mjs \
  apps \
  apps/api \
  apps/api/tsconfig.json \
  apps/api/src \
  apps/api/src/scripts \
  apps/api/src/scripts/runtime-data-maintenance.ts \
  apps/api/src/scripts/initialize-first-backoffice-password.ts; do
  test ! -L "$path"
  { test -f "$path" || test -d "$path"; }
  test "$(stat -c %u "$path")" = "$(id -u)"
  chmod go-w "$path"
done
```

拉取发布分支：

```bash
umask 077
git fetch origin
git pull --ff-only origin codex/UI
```

如果服务器直连 GitHub 出现 TLS 中断，可临时使用服务器本机代理：

```bash
umask 077
git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 fetch origin
git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 pull --ff-only origin codex/UI
```

## 4. 公网服务器构建和运行

拉取后安装依赖。若 `package-lock.json` 有变化，必须重新安装依赖。维护运行器会拒绝组或其他用户可写的依赖链，因此必须先把本次发布 shell 的 umask 收紧为仅服务用户可写：

```bash
umask 077
npm ci
# npm ci 可能保留旧顶层目录的权限；维护运行器要求整条依赖链仅服务用户可写。
test -d node_modules && test ! -L node_modules
test "$(stat -c %u node_modules)" = "$(id -u)"
chmod 700 node_modules
```

以专用、不可登录的 API 服务用户确认运行数据目录、上传目录和备份目录为私有本地目录；所有祖先目录不得包含符号链接或由非服务用户写入：

```bash
umask 077
install -d -m 700 apps/api/runtime-data apps/api/runtime-uploads apps/api/runtime-backups
npm run verify:api-data
```

构建前建议先跑类型检查：

```bash
npm run typecheck --workspaces --if-present
npm run build --workspaces --if-present
npm run build:public-web
```

最后一条必须在全量构建之后执行：全量工作区构建会按默认根路径生成移动 H5，而公网静态服务把移动端挂在 `/mobile/`；公网静态构建会重新生成后台和 `/mobile/` 专用移动产物，避免移动页面返回 `200` 但误取后台的 `/assets/*`。

### Spark 受管 API 启动

构建通过后，先启动已在受控停写窗口中停止的 API，并确认回环健康检查；未通过时不得启动静态服务或私网中继，更不能进入 VNC 切流阶段：

```bash
systemctl --user start "$API_SERVICE"
systemctl --user is-active --quiet "$API_SERVICE"
curl -fsS http://127.0.0.1:8100/api/health >/dev/null
```

### Spark 受管公网应用服务（当前最终方案）

Spark 通过现有 HTTPS 反向代理提供后台和移动 H5 时，静态服务必须由 systemd 用户服务托管，不能用 `nohup` 或临时 `npx serve`。首次部署可使用版本库中的受控单元模板：

```bash
loginctl show-user "$USER" -p Linger
install -D -m 644 deploy/systemd/vending-public-web.service \
  "$HOME/.config/systemd/user/vending-public-web.service"
systemctl --user daemon-reload
STATIC_SERVICE=vending-public-web.service
STATIC_REPO_DIR="$(systemctl --user show "$STATIC_SERVICE" -p WorkingDirectory --value)"
test "$STATIC_REPO_DIR" = "$REPO_DIR" || {
  echo '静态服务与受管 API 未指向同一发布工作树。' >&2
  exit 1
}
systemctl --user enable --now vending-public-web.service
systemctl --user is-active --quiet vending-public-web.service
curl -fsS -o /dev/null http://10.66.66.2:5795/
test "$(curl -sS -o /dev/null -w '%{http_code}' http://10.66.66.2:5795/api/health)" = 403
```

`Linger` 必须为 `yes`，否则用户退出后 systemd 用户服务不能保证常驻。该服务仅绑定 Spark 的 RFC1918/WireGuard 地址 `10.66.66.2:5795`，由 VNC 的受控 HTTPS Nginx 访问；它不会直接绑定公网地址。Spark 本机不是 API relay 的授权来源，所以本机直连 `:5795/api/health` 必须返回 `403`；这证明来源门禁仍在，不能作为发布失败依据。只有从 VNC `10.66.66.1` 经受管转发请求时，根页面和 `/api/health` 才都必须返回 `200`。若运行网络不同，必须先在代码允许的 loopback 或 RFC1918 私网地址范围内调整受控单元，再进行反代验证。

### 历史：Spark 私网 API 中继（不用于本次最终入口）

当 API 启用 `TRUST_PROXY_HOPS=1` 时，API 必须保持 `API_HOST=127.0.0.1`；不能为了恢复 WireGuard 访问而关闭信任代理门禁或把 API 重新绑定到私网地址。Spark 候选当前的受管 API 使用 `PORT=8100`，由版本库中的受管中继把受控 HTTPS 代理的一跳请求转到该回环 API：

```bash
install -D -m 644 deploy/systemd/vending-private-api-relay.service \
  "$HOME/.config/systemd/user/vending-private-api-relay.service"
systemctl --user daemon-reload
API_RELAY_SERVICE=vending-private-api-relay.service
API_RELAY_REPO_DIR="$(systemctl --user show "$API_RELAY_SERVICE" -p WorkingDirectory --value)"
test "$API_RELAY_REPO_DIR" = "$REPO_DIR" || {
  echo 'API 私网中继与受管 API 未指向同一发布工作树。' >&2
  exit 1
}
systemctl --user enable --now "$API_RELAY_SERVICE"
systemctl --user is-active --quiet "$API_RELAY_SERVICE"
curl -fsS http://127.0.0.1:8100/api/health >/dev/null
ss -lntp | grep -E '127\.0\.0\.1:8100|10\.66\.66\.2:8100'
```

该中继固定监听 `10.66.66.2:8100`，接受 VNC WireGuard 对端 `10.66.66.1`，再转到 `127.0.0.1:8100`。同一端口号位于两个不同绑定地址，不会形成自转发。为保持现有只读健康网关，`10.66.66.2` 仅可无控制头读取精确的 `GET /api/health` 与 `GET /api/health/production-readiness`；它不能借此访问其他 API。

所有普通转发请求都必须同时满足来源地址、允许域名、`https` 协议和值班期间专门生成的服务间共享令牌。令牌文件是启动硬门槛：Spark 保持服务账户私有目录；VNC 使用 root:vnc、`0710` 的 `/etc/vending/credentials/vnc` 与 vnc:vnc、`0600` 的令牌文件，只允许 VNC 服务账户读取。不得放进 Git、环境变量、命令行、日志或聊天记录。令牌生成、两机分发和一致性核验只能通过受控的主机内或主机到主机秘密通道完成，核验时只报告文件存在性、属主和权限，不显示内容或摘要。

中继会删除所有客户端带入的 `Forwarded`、`X-Forwarded-*`、`X-Real-IP` 和内部控制头，只接受 VNC API edge 用该令牌重新生成的单值控制头，并重新生成 API 所见的 `X-Forwarded-For`、`X-Forwarded-Host`、`X-Forwarded-Proto`。Spark 本机直接访问 `10.66.66.2:8100` 的普通业务请求会得到 `403`，这是预期行为；应在 API 回环健康检查、受控 VNC edge 路径和最终 HTTPS 地址三个位置分别验证。即使部署环境不再使用防火墙，中继自身的来源与令牌校验也必须保留。

### 历史：VNC 回环边缘中继（不用于本次最终入口）

VNC API edge 不允许以 TCP loopback 作为可信来源。切流需要 root 受管地把 HTTPS Nginx 的 `/api/` upstream 改为专用 Unix socket；静态 `/` 仍可通过受管的 `127.0.0.1:5795` **转发器**访问 Spark 静态服务。最终态是“Spark 运行实际 vending API/静态应用，VNC 只保留 Nginx 和必要受控转发”；旧 VNC 直跑 API/静态业务只在新链路验收后退出。**这是第二主机阶段：先完成 Spark API、静态服务、私网 API 中继的启动和本机验证，再返回本节。**在 VNC 进入维护窗口前，root 只执行零参数 `vending-public-ingress-prepare`：建立专用 socket 目录并写入 root 托管的 VNC 令牌，但不修改 vhost 或 reload。Git 快进、API edge socket 本机验证通过后，root 才执行零参数 `vending-public-ingress-activate` 安装版本库片段、执行 `nginx -t`、有效 server-block 合同校验和 reload。任一前置条件不满足都不得停止 VNC 的旧服务或更新其工作树。

```text
HTTPS Nginx
  /api/ -> /run/vending/api-edge.sock -> VNC API edge -> 10.66.66.2:8100 -> Spark API relay -> 127.0.0.1:8100
  /     -> 127.0.0.1:5795 -> VNC static edge -> 10.66.66.2:5795 -> Spark static service
```

VNC 工作树必须是既有的受管目录，且只能通过 Git 快进更新；运行数据恢复目录、备份目录和其他未跟踪用户文件不得删除、暂存或覆盖。若需新发布目录，只能从既有受管仓库以 Git worktree 建立版本化 release，并通过可回退的受管服务引用，不能直接复制目录或新 clone。先逐一核对当前占用 `127.0.0.1:4000`、`127.0.0.1:5795` 的旧进程的 PID、命令行、工作目录、cgroup 与实际管理器；若发现 systemd、supervisor、PM2 或其他自动重启器，先停止该管理器，不能只杀子进程。旧 API 的 `127.0.0.1:4000` 必须在 root Nginx socket 切换成功前保留为回退 upstream；静态旧监听仅在替换其 `5795` 端口前进入维护窗口。对没有受管重启和回退路径的 session 进程，必须先建立并在备用端口验证 user systemd 服务及回退服务，才可进入维护窗口。

```bash
set -euo pipefail
REPO_DIR=/home/vnc/vending-release-current
cd "$REPO_DIR"
curl --noproxy '*' -fsS -o /dev/null http://10.66.66.2:18100/api/health
curl --noproxy '*' -fsS -o /dev/null http://10.66.66.2:5795/
git diff --quiet --exit-code && git diff --cached --quiet --exit-code || {
  echo '检测到追踪文件改动；保留现状并停止发布。' >&2
  exit 1
}
git status --short
PREVIOUS_RELEASE="$(git rev-parse HEAD)"
umask 077
git fetch origin
git pull --ff-only origin codex/UI
npm ci
test -d node_modules && test ! -L node_modules
test "$(stat -c %u node_modules)" = "$(id -u)"
chmod 700 node_modules
npm run build
npm run build:public-web
loginctl show-user "$USER" -p Linger | grep -qx 'Linger=yes'
test -r /etc/vending/credentials/vnc/private-api-relay.token
test "$(stat -c '%U:%G %a' /etc/vending/credentials/vnc)" = 'root:vnc 710'
test "$(stat -c '%U:%G %a' /etc/vending/credentials/vnc/private-api-relay.token)" = 'vnc:vnc 600'
test "$(stat -c %a /run/vending)" = 2710
install -D -m 644 deploy/systemd/vending-public-api-edge-relay.service \

  "$HOME/.config/systemd/user/vending-public-static-edge-relay.service"
install -D -m 644 deploy/systemd/vending-local-api-fallback.service \
  "$HOME/.config/systemd/user/vending-local-api-fallback.service"
```

前两条 WireGuard 请求是 Spark 就绪硬门禁；第一条只通过既有的 `10.66.66.2:18100` 只读健康网关检查，不得改为让 VNC 直连需要服务令牌的私网 API relay `:8100`。追踪文件改动、构建、令牌私有权限或 root 受管 socket 目录任一失败都会在 Git 更新前停止。未跟踪运行数据/恢复/备份目录可以保留，但只记录，不得作为本次提交内容。`Linger=yes` 是用户服务常驻门禁。上述单位安装到 `$HOME/.config/systemd/user` 并由 `systemctl --user` 管理，进程身份继承 VNC 用户管理器；不要把它们改成系统 unit 或额外设置 `User=`/`Group=`。`PREVIOUS_RELEASE` 必须记入发布记录；旧 `127.0.0.1:4000` API 在 root Nginx socket 切换后的短暂验证窗口中保留为回退 upstream，不得被误认为新版本的数据平面。

API edge 只监听 `/run/vending/api-edge.sock`，不监听任何 TCP API 端口。该目录必须由 root tmpfiles 以 `vnc:www-data`、`2710` 创建并带 setgid；socket 由 `vnc` 服务创建为同组 `www-data`、`0660`，Nginx worker 可以连接，其他本机账户不能遍历目录或连接 socket。因为 socket 本身是唯一可鉴别入口，API edge 才允许信任 root Nginx 覆盖写入的 `Host $host`、`X-Real-IP $remote_addr`、`X-Forwarded-Proto $scheme`，再删除客户端带入的转发头、附加 VNC/Spark 服务间令牌并转到 Spark。静态 edge 仍只绑定 VNC 回环地址、只转发到 Spark 静态服务并对 `/api/*` 失败关闭。它们不会新增全功能公网监听端口。切换前必须由 root action 用密封版本库片段替换有效 vhost 的 `/api/` location；action 会在 reload 前内部执行 `nginx -t` 与有效 server-block 合同校验。

在进入 VNC 维护窗口前，root 受管身份先执行受审计的 `vending-public-ingress-prepare`。它创建目录后仍不改 Nginx。Git 快进后先启动 API edge，并用 `namei -l /run/vending/api-edge.sock` 核对路径；随后 root 执行 `vending-public-ingress-activate`。activate 会逐项核对：全部非 root 的 `nginx` worker 必须使用 `www-data:www-data`；`/run/vending` 必须精确为 `vnc:www-data 2710`；socket 必须精确为 `vnc:www-data 660`；`admin` 不得属于 `www-data`；以 `www-data` 身份的正向 socket 请求必须成功、`admin` 反向请求必须被拒绝。仅当上述条件、`nginx -t` 与有效 server-block 合同均通过时，activate 才会 reload。任一失败都禁止切流并恢复已替换的 fragment/vhost。旧本地回退服务 disable 前，必须先成功执行零参数、受审计的 `vending-public-ingress-rollback-readiness`：它只核验当前 sealed fragment/vhost、root-only 归档、`nginx -t` 与有效合同，不替换文件或 reload。若该检查拒绝，禁止手改 Nginx 或停旧服务；保留 Spark 链路并由 root 重新密封计划。若已成功切流后需要恢复同一密封计划的旧 Nginx 配置，只能执行零参数、受审计的 `vending-public-ingress-rollback`；它拒绝 drift，不改 tmpfiles、令牌或 Spark 数据面。合同验证同一个 `vending.5gogogo.top` server block 中的 `/api/` 和 `/` location 同时包含正确 upstream 与覆盖头，不会以分散字符串匹配替代信任链验证。切流后仍必须以公网 HTTPS 的实际 API/页面回归为准。

普通 VNC 或 `admin` 本机用户不得获得 `/run/vending` 的组成员资格，也不得在该目录下创建、替换或连接 socket。服务间令牌只用于 VNC API edge 到 Spark 私网中继，不能代替 Unix socket 的 ingress 身份边界。若 socket 权限、Nginx worker 组或 root 配置不可核验，必须停止发布，不能退回 loopback TCP API edge。

完成前述 Spark、root socket、Git 更新和构建门禁后，先启动 API edge 到 Unix socket，并在不改 Nginx 前完成本机正向检查。旧 `127.0.0.1:4000` API 此时仍保留，只有在 root 配置切换成功且公网验证稳定后才按独立维护流程停止。静态 edge 的 `5795` 切换必须另行完成旧静态进程身份记录、受管回退演练和短维护窗口；它不改变 Spark 数据平面。

```bash
systemctl --user start vending-public-api-edge-relay.service
systemctl --user is-active --quiet vending-public-api-edge-relay.service
curl --unix-socket /run/vending/api-edge.sock -fsS \
  -H 'Host: vending.5gogogo.top' \
  -H 'X-Real-IP: 198.51.100.1' \
  -H 'X-Forwarded-Proto: https' \
  http://vending.5gogogo.top/api/health >/dev/null
test "$(curl --unix-socket /run/vending/api-edge.sock -sS -o /dev/null -w '%{http_code}' \
  -H 'Host: vending.5gogogo.top' http://vending.5gogogo.top/api/health)" = 403
```

root 完成 Nginx socket 切换后，静态 edge 需要在一个短维护窗口接管 `127.0.0.1:5795`。先记录并确认当前监听确实由下面这个**具体** VNC user service 管理；若不是，停止并补齐对应的受管回退路径，不能猜测或杀端口。确认后才优雅停止旧静态回退、启动 Spark 静态转发器；任一启动、本机回归或旧 service 禁用失败都立即恢复同一旧 service。这里的 `disable` 只移除旧 unit 的默认自动启动，是**可逆的 handover 互斥锁**，不是最终退役或删除：旧 unit/checkouts 继续保留，任一失败分支都以 `enable --now` 恢复。它必须在新 edge 健康后立即完成，否则 VNC user manager 重启时旧静态会重新争抢 `5795`：

```bash
set -euo pipefail
OLD_STATIC_SERVICE=vending-local-static-fallback.service
NEW_STATIC_SERVICE=vending-public-static-edge-relay.service
systemctl --user is-active --quiet "$OLD_STATIC_SERVICE"
systemctl --user show "$OLD_STATIC_SERVICE" \
  -p MainPID -p ExecStart -p WorkingDirectory -p FragmentPath
systemctl --user stop "$OLD_STATIC_SERVICE"
if ! systemctl --user start "$NEW_STATIC_SERVICE" || \
  ! systemctl --user is-active --quiet "$NEW_STATIC_SERVICE" || \
  ! curl -fsS -H 'Host: vending.5gogogo.top' http://127.0.0.1:5795/ >/dev/null || \
  test "$(curl -sS -o /dev/null -w '%{http_code}' -H 'Host: vending.5gogogo.top' http://127.0.0.1:5795/api/health)" != 404; then
  systemctl --user stop "$NEW_STATIC_SERVICE" || true
  systemctl --user start "$OLD_STATIC_SERVICE"
  exit 1
fi
if ! systemctl --user disable "$OLD_STATIC_SERVICE" || \
  systemctl --user is-enabled --quiet "$OLD_STATIC_SERVICE"; then
  systemctl --user stop "$NEW_STATIC_SERVICE" || true
  systemctl --user enable --now "$OLD_STATIC_SERVICE"
  exit 1
fi
```

若 API edge 未启动、socket 检查失败或 Nginx reload 后公网回归失败，root 必须立即执行固定 `vending-public-ingress-rollback` 恢复同一密封计划记录的旧 `/api/ -> 127.0.0.1:4000` location；旧本地 API 仍在短暂回退窗口内，随后再按独立版本恢复流程处理。若静态 edge 未启动或本机回归失败，先停止静态 edge 并用已验证的旧静态受管服务恢复 `127.0.0.1:5795`。任何失败都要保留错误日志与旧进程身份记录，不能用按端口批量强杀替代回退：

```bash
systemctl --user stop vending-public-static-edge-relay.service
systemctl --user enable --now vending-local-static-fallback.service
systemctl --user is-active --quiet vending-local-static-fallback.service
curl -fsS http://127.0.0.1:5795/ >/dev/null
```

不要通过暴露 Spark 原始端口临时绕过。root Nginx 只允许按本节的 Unix socket 合同受管变更；切流成功后立即继续公网 HTTPS 验收。

### VNC 旧业务运行时退役（仅在公网验收通过后）

最终架构不保留 VNC 上直跑的 vending API 或静态业务：Spark 运行实际应用，VNC 只保留 Nginx、API Unix-socket edge、静态转发器，以及可选的仅跳转 `:5795` 入口。退役必须在 HTTPS 页面、同源 API、管理员后台和必要角色流均已通过公网回归后进行；在此之前，旧 `127.0.0.1:4000` API 仍是受控回退，不得提前停止。

退役前先创建 [旧运行时退役记录模板](../deploy/admin-actions/vending-legacy-runtime-retirement.record.template.md)，至少连续观察切流后的公网 HTTPS 30 分钟、完成第二次独立回归，并记录 Spark 提交、root action 计划 SHA、旧进程 PID、命令行、工作目录、cgroup、unit、fragment 路径和管理器。紧邻 `disable --now` 前，必须同时确认 API edge、静态 edge、Unix socket 与 `127.0.0.1:5795` 转发仍可用，并成功运行 `sudo /usr/local/sbin/vending-public-ingress-rollback-readiness`。该命令会拒绝 Nginx drift、缺失归档或不完整有效合同；若拒绝，禁止手改 Nginx 或停旧服务，保留 Spark 链路并由 root 重新密封计划。模板中的候选 unit 只是在已核验模板成立时才可使用；执行前必须逐项比对 `LoadState`、`WorkingDirectory` 与 `FragmentPath` 是否和记录完全一致。若实机服务名、工作目录、fragment、管理器或回退路径不一致，停止退役。禁止猜测服务名、按端口批量 kill，或把非 vending 进程纳入本次操作。

只有记录中的两个旧 vending user service 已确认可回退时，才可执行最终的优雅 stop/disable；旧静态 unit 在 handover 互斥锁阶段已 disabled，最终命令只是再次确认其停用状态。旧 checkout、unit 文件和其依赖必须保留至少 7 个自然日，不能在切流当天删除：

```bash
set -euo pipefail
OLD_API_SERVICE=vending-local-api-fallback.service
OLD_STATIC_SERVICE=vending-local-static-fallback.service

systemctl --user is-active --quiet vending-public-api-edge-relay.service
systemctl --user is-active --quiet vending-public-static-edge-relay.service
test -S /run/vending/api-edge.sock
curl --unix-socket /run/vending/api-edge.sock -fsS \
  -H 'Host: vending.5gogogo.top' \
  -H 'X-Real-IP: 198.51.100.1' \
  -H 'X-Forwarded-Proto: https' \
  http://vending.5gogogo.top/api/health >/dev/null
curl -fsS -H 'Host: vending.5gogogo.top' http://127.0.0.1:5795/ >/dev/null
sudo /usr/local/sbin/vending-public-ingress-rollback-readiness
systemctl --user show "$OLD_API_SERVICE" \
  -p MainPID -p ExecStart -p WorkingDirectory -p FragmentPath -p LoadState
systemctl --user show "$OLD_STATIC_SERVICE" \
  -p MainPID -p ExecStart -p WorkingDirectory -p FragmentPath -p LoadState
systemctl --user disable --now "$OLD_API_SERVICE" "$OLD_STATIC_SERVICE"
if systemctl --user is-active --quiet "$OLD_API_SERVICE"; then
  exit 1
fi
if systemctl --user is-active --quiet "$OLD_STATIC_SERVICE"; then
  exit 1
fi
if systemctl --user is-enabled --quiet "$OLD_API_SERVICE"; then
  exit 1
fi
if systemctl --user is-enabled --quiet "$OLD_STATIC_SERVICE"; then
  exit 1
fi
```

退役后核对：旧 API 不再监听 `127.0.0.1:4000`；`127.0.0.1:5795` 若仍监听只能属于 `vending-public-static-edge-relay.service`；API edge、静态 edge、Nginx、VNC 和退役记录中列出的其他业务服务仍 active。失败或公网回归异常时，按以下固定顺序恢复，先让旧 API 健康，再恢复 Nginx，避免把公网入口指向未启动的回退 upstream：

```bash
set -euo pipefail
OLD_API_SERVICE=vending-local-api-fallback.service
OLD_STATIC_SERVICE=vending-local-static-fallback.service

systemctl --user enable --now "$OLD_API_SERVICE"
systemctl --user is-active --quiet "$OLD_API_SERVICE"
curl -fsS http://127.0.0.1:4000/api/health >/dev/null
sudo /usr/local/sbin/vending-public-ingress-rollback
systemctl --user stop vending-public-api-edge-relay.service

systemctl --user stop vending-public-static-edge-relay.service
systemctl --user enable --now "$OLD_STATIC_SERVICE"
systemctl --user is-active --quiet "$OLD_STATIC_SERVICE"
curl -fsS -H 'Host: vending.5gogogo.top' http://127.0.0.1:5795/ >/dev/null
```

这里的 unit 名称只在退役记录已确认其准确性时使用；实际名称不同则使用记录中的准确名称替换变量，不能扩大为通配符。回退后重新执行 HTTPS 页面和 API 健康回归，并记录原因与结果。任何异常都只恢复已记录的 vending 回退服务，不得影响其他 VNC 业务。

### HTTP 端口入口别名（可选）

若验收方必须从 `http://5gogogo.top:5795/` 开始访问，只能把该端口作为**无状态入口别名**：只接受不带查询参数的根路径 `GET /` 或 `HEAD /`，固定返回 `308` 到 `https://vending.5gogogo.top/`；其他路径、查询参数和所有非导航方法一律拒绝。它绝不转发登录、验证码、Cookie、Bearer token 或任何 `/api/*` 写请求。登录与全部业务流程仍在受保护的 HTTPS 主站完成；`https://5gogogo.top:5795/` 不是本方案的一部分。

启动前必须分别确认公网 NAT 确实落到 VNC 的受管 RFC1918 地址、该地址上的 `5795` 未被其他监听占用、以及云安全组或主机防火墙已明确放行这个仅作跳转的 HTTP 端口。不能为了“端口可达”把 Spark 静态服务、API 或 Node 全功能网关直接暴露到公网。通过上述检查后才可安装并启动受管跳转服务：

```bash
install -D -m 644 deploy/systemd/vending-public-http-entry-redirect.service \
  "$HOME/.config/systemd/user/vending-public-http-entry-redirect.service"
systemctl --user daemon-reload
systemctl --user enable --now vending-public-http-entry-redirect.service
systemctl --user is-active --quiet vending-public-http-entry-redirect.service
curl -fsS -o /dev/null -w '%{http_code}\n' \
  -H 'Host: 5gogogo.top:5795' http://172.24.14.210:5795/
```

本机检查只能证明受管服务监听正确地址；最终仍必须从独立公网网络确认 `http://5gogogo.top:5795/` 的 `308 Location` 精确指向固定 HTTPS 主站，再在 HTTPS 主站完成页面、同源 API 和登录回归。

公网机器内存较小时，继续保持上一节的优雅停写状态，避免同时运行两套 API 或后台服务。不得以 `fuser -k` 强制杀掉可能仍在完成金融任务的进程；若优雅停止超过运维超时，先记录进程、租约和错误证据，再按当前进程管理器的受控升级流程处理。

Spark API、静态服务与私网中继已按本节前面的顺序启动并验活；不要在已使用 systemd 停止服务的同一环境改用 `nohup`，以免产生双实例。VNC edge 只可在这些 Spark 门禁通过后才开始其独立维护窗口。

生产环境启动前必须确认：

- `NODE_ENV=production` 时不会加载 `.env.example`。
- `NODE_ENV` 或 `APP_ENV` 任一声明 `production` 都会启用严格门禁；即使另一个变量误写成 `development` 也不会降级。
- `PUBLIC_BASE_URL` 是公网 HTTPS 地址。
- `CORS_ORIGINS` 只包含可信 HTTPS 前端来源。
- `VM_DATA_PLANE=live`，并由独立 `VM_DATA_ROOT` / `VM_DATA_PLANE_ID` 派生业务数据、审计、上传、备份和金融租约路径；`VM_PLATFORM_TENANT_NAME` 已设置，且真实库中唯一客户实例的 ID、URL、名称分别与 `VM_DATA_PLANE_ID`、`PUBLIC_BASE_URL`、该名称一致。
- `VERIFICATION_CODE_PROVIDER` 必须是 `aliyun_pnvs` 或 `manual`，且验证码预览关闭。PNVS 模式要求用途方案审核完成；人工码模式要求后台签发、短期有效、失败计数、撤销和单次消费全部可用。
- 预约取货正式实例可设置 `VM_RESERVATION_ONLY_PICKUP=true` 与 `PAYMENT_MODE=disabled`，此时支付/退款账本必须为空且不要求支付渠道；其他正式实例必须设置 `PAYMENT_MODE=real` 并通过微信/支付宝真实配置自检。任何正式实例都不能使用 `auto` 或 `mock`。
- JSON 账本阶段必须显式设置 `FINANCIAL_SINGLE_WRITER_ENABLED=true`、`WEB_CONCURRENCY=1`、`API_INSTANCE_COUNT=1`，并保持 `NODE_APP_INSTANCE` 为空或 `0`；不得启用 cluster、多工作者或双写者。只有 `PAYMENT_MODE=real` 时必须启用自动对账。
- 系统审计日志所在目录必须只允许 API 运行用户安全写入；POSIX 上每次追加记录在返回成功前都会同步文件和父目录。禁止外部 `copytruncate` 或未纳入备份清单的日志轮替；在实现受控分段轮替前，必须监控审计盘空间。生产启动会写入受控启动审计；每个非只读 HTTP 请求会先写入不含请求体、查询参数和密钥的最小审计意图，再进入处理器和业务持久化。系统设置/AI 配置落盘、真实 SmartVM 外发命令与支付自动对账周期还会在服务边界再次写入意图，避免绕过 HTTP 入口。
- 任一意图写入失败都会返回不泄密的 `503`，且不得执行对应副作用。完成记录失败不会把已经完成的业务伪装成失败或诱导客户端重试，但会锁存审计不可用、使后续业务请求和生产就绪检查返回 `503`；修复介质后必须重启服务。
- 运行数据与系统审计日志均为备份强制项；缺失任一项、或备份清单未纳入审计日志时，`verify:api-data` 与 `backup:api-data` 必须失败。系统设置不能在线切换数据、审计、上传、备份或金融租约路径；只能在停服维护窗口通过受控部署配置统一变更并重启。
- 生产启动与运行数据维护命令会拒绝数据、审计、上传、备份、金融租约路径之间的重叠，以及现有路径链中的符号链接。该预检不替代服务用户所有权、ACL、Windows reparse point 与批准存储根的人工门禁。
- 检测到恢复遗留的同级 `staging` / `rollback` 文件或目录时，生产启动会拒绝加载。这是防止自动重启读取混代数据的停止门禁，不等同于跨资源断电事务；可恢复 journal 与断电故障注入演练完成前，恢复能力仍是上线阻碍。
- 有柜机时 `SMARTVM_MODE=real`、生产凭据完整且未签名回调关闭；零柜机正式实例可设为 `disabled`，但不得保留 SmartVM 地址、来源或凭据，且生产就绪检查必须确认设备数为零。
- 默认后台密码账号已改密或移除。

## 4.1 公网/预发布外部服务预检

API 服务启动后，必须在公网服务器或能读取同一套 `.env` 的运维环境里执行外部服务预检。该脚本会复用项目现有支付自检规则、生产环境安全检查约束和 `sandbox` 的 SmartVM / 短信能力，默认生成 JSON 和 HTML 两份报告：

管理员 Bearer Token 只允许通过进程环境或权限受限的 `sandbox/.env.local` 提供，脚本不接受命令行 token 参数，避免凭据进入 shell 历史和进程参数列表。

```bash
npm run sandbox:external-preflight -- \
  --profile=production \
  --api-base-url https://vending.5gogogo.top/api \
  --skip-smartvm-probe
```

预发布环境使用：

```bash
npm run sandbox:external-preflight -- \
  --profile=preprod \
  --api-base-url https://<预发布域名>/api \
  --device-code <预发布测试柜机编号>
```

需要真实发送一条短信验证码时，必须显式追加手机号：

```bash
npm run sandbox:external-preflight -- \
  --profile=production \
  --api-base-url https://vending.5gogogo.top/api \
  --device-code 91120149 \
  --send-sms \
  --sms-phone 13800138000
```

预检结果要求：

- SmartVM：`real` 模式下签名凭据不能是 sandbox 演示值，未签名回调必须关闭，并且指定测试柜机的商品只读接口必须通过；`disabled` 只允许零柜机正式实例，地址、来源和凭据必须为空，预检不会请求外部平台。
- 验证码：PNVS 模式要求密钥、签名、模板和用途方案完整，真实发送只在显式 `--send-sms` 时执行；人工码模式不发送短信，改为验证后台签发和单次消费。
- 支付：`PAYMENT_MODE=real` 时要求微信和支付宝配置及 HTTPS 回调完整；预约取货的 `PAYMENT_MODE=disabled` 要求支付/退款账本为空，并跳过渠道配置检查。
- 公网 API：`/api/health` 可访问，未登录读取 `/api/payments/diagnostics` 会被拒绝；通过安全环境配置提供管理员 token 时，还会从公网 API 拉取后台支付自检结果。
- 受控反代门禁：在 Spark 候选上直接访问 `/api/health/production-readiness` 必须返回 `200`。该端点在开发环境、模拟柜机/支付、默认后台凭据或任一生产安全门禁不满足时固定返回不泄密的 `503`，因此普通健康检查 `200` 不能作为公网切流依据。
- 预检整体结果不得为“失败”；若存在“警告”，发布记录必须写明原因和是否接受；若存在“失败”，不得继续认定发布完成。

脚本输出的 HTML 报告位于 `sandbox/reports/`，例如：

```text
sandbox/reports/external-service-preflight-<时间>.html
```

发布记录必须附上本次预检命令、整体结果和报告路径。报告不会输出支付、短信或 SmartVM 密钥。

## 5. 公网部署验证

服务启动后，先在服务器本机确认端口和健康检查：

```bash
curl -fsS http://127.0.0.1:8100/api/health
systemctl --user is-active --quiet vending-private-api-relay.service
test "$(curl -sS -o /dev/null -w '%{http_code}' http://10.66.66.2:5795/api/health)" = 404
ss -lntp | grep -E '127\.0\.0\.1:8100|10\.66\.66\.2:(8100|5795)'
```

默认静态服务只绑定 `127.0.0.1:5795`，适用于页面和 API 在同一台机器的反代。Spark 私网部署模板会显式让静态服务绑定 `10.66.66.2:5795`、让 API 中继绑定 `10.66.66.2:8100`。在当前双主机链路中，VNC 的 root Nginx 把页面请求转到本机静态 edge、把 `/api/` 单独转到受保护的 Unix socket，并且只覆盖 `Host`、`X-Real-IP`、`X-Forwarded-Proto`；VNC API edge 验证该 socket 入口后，才生成 `X-Vending-Relay-*` 内部控制头与服务间令牌并转给 Spark。外层 Nginx 不得直接写入任何 `X-Vending-Relay-*` 头。静态服务不会代理 `/api/*`，直接访问其 `/api/*` 返回 `404` 是预期的失败关闭，不得把它当成 API 健康检查。

同时查看 API 启动日志里的支付自检摘要：

```bash
tail -n 80 apps/api/runtime-data/api.log | grep '支付自检'
```

再确认外部服务预检已经通过，并记录 HTML 报告路径：

```bash
ls -lt sandbox/reports/external-service-preflight-*.html | head -n 3
```

确认恢复后的或发布后的运行数据仍能通过基本校验：

```bash
npm run verify:api-data
```

然后必须从公网地址验证：

```text
https://vending.5gogogo.top/api/health
https://vending.5gogogo.top/api/health/production-readiness
https://vending.5gogogo.top/
```

公网验证至少覆盖：

- 后台登录页能打开，接口请求指向公网 API。
- 后台账号登录、权限菜单、系统设置只读/可写权限表现正确。
- 小程序或体验版使用公网 `VITE_API_BASE_URL`。
- 验证码不会在公网响应和页面中暴露。
- 未登录访问受保护接口会被拒绝。
- 设备、货物、人员、日志等核心页面能正常加载。
- 支付和柜机相关流程至少确认配置状态；支付状态以 `[支付自检]` 启动日志或后台“系统设置 / 支付自检”为准，真实支付/真实柜机未执行时必须在发布记录中说明。
- `/api/health/production-readiness` 必须返回 HTTP 200 和最小就绪结果；普通 `/api/health` 返回 200 只能证明进程存活，不能替代生产就绪结论。
- 柜机回调日志与系统审计只保留脱敏摘要和不可逆重放指纹；发布前检查运行数据中不再保留原始签名、手机号、交易号或回调 URL 查询参数。

只有公网验证通过，才算本次发布完成。

## 6. 失败处理

如果公网验证失败：

1. 先记录当前服务器 commit、错误接口、错误页面和日志片段。
2. 判断是环境配置问题还是代码问题。
3. 环境配置问题在服务器 `.env` 或进程配置里修正，不提交真实密钥。
4. 代码问题回到本地修复，重新走“本地验证 -> Git 提交 -> 公网拉取 -> 构建运行 -> 公网验证”。
5. 需要回滚时，回到上一发布 commit，重新安装、构建、启动，并重新做公网验证。

如果需要恢复发布前运行数据，先停止 API，再恢复拉取前生成的 `pre-release` 备份：

```bash
systemctl --user stop <api-service>
npm run verify:api-data -- --backup apps/api/runtime-backups/<备份目录名>
npm run restore:api-data -- --backup apps/api/runtime-backups/<备份目录名> --yes
systemctl --user start <api-service>
curl -sS <受管 API 健康检查地址>
npm run verify:api-data
```

不要在公网服务器上直接热改源码来修复代码问题。

## 7. 测试柜到位后的受控联调

测试柜编号和供应商回调登记完成后，先在 Spark 候选或独立预发布环境使用权限受限的私密环境文件运行只读预检。默认只允许签名商品查询和状态读取；不得自动开门、结算、补扣、短信、真实支付、退款或 AI 外呼。

本仓库的 `simulate-door-status`、`simulate-settlement` 与 `simulate-latest-event` 脚本只接受本机 loopback 候选 API。即使遗留环境变量尝试放行远端地址，脚本也会在发起请求前失败。需要对真实测试柜进行任何写操作时，必须改走明确记录、单独审批的预发布流程，而不是绕过此保护。
